The first three paths work with scientific declarations, Python, and configuration. The last three involve Rust and identify the small part of the native code you need to understand.

For protocol presentation, start with the [document generation boundaries](/docs/compiler/architecture#protocol-documents): the Typst style sheet controls typography, and the document model and its producers control content.

## Choose the right instrument contribution

These paths solve different problems. A new instrument integration may need all three; an improvement to an existing integration usually starts with whichever part is missing.

| Your situation                                                                                         | Choose                                                          | What you contribute                                                                                                        |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Lab supports your Hamilton STAR, and you want to share your measured aspiration settings.              | [An instrument profile](/docs/contributing/instrument-profiles) | Configuration and liquid-class data, their provenance, and an example showing that the settings reach the generated files. |
| Lab can describe transfers and mixes, but cannot produce instructions for your liquid handler.         | [An adapter](/docs/contributing/adapters)                       | Rust code that checks whether the instrument can perform those operations and generates its instruction files.             |
| Lab can generate a cycler's run document, and you want Lab to send the commands and report completion. | [Execution support](/docs/contributing/execution-support)       | A document loader and executor, using a device driver for communication, plus progress and failure handling.               |

For one instrument, the **profile** describes its configuration, the **adapter** generates instructions for it, and **execution support** carries those instructions out. A driver or vendor SDK supplies device communication; it does not by itself teach Lab how to generate a suitable protocol.

File generation is useful without direct execution from Lab. For example, the current Opentrons adapters produce files for vendor tooling; they do not run the robot through `lab run`. Add execution support when you want Lab to operate the device and record its progress. The [instrument support matrix](/docs/status#device-implementation-matrix) shows which parts already exist.

If you want a new pipetting recipe on an already-supported robot, start with [Write a pipetting method](/docs/contributing/pipetting-methods). You usually do not need a new adapter. If you only need to describe an instrument's identity, location, or available capabilities, start with [facility inventory](/docs/compiler/facility-planning#describe-the-laboratory).

## Try a complete contribution

If you already write Python, begin with [the pipetting method](/docs/contributing/pipetting-methods). Its authoring API starts with:

```python
from lab.procedures import pipetting as p
```

The working example has four parts: an action declaration, a Python implementation of its liquid operations, a generated method catalog, and a Python workflow consuming that action. You can change the preparation, regenerate its catalog, and refine the workflow without touching compiler internals.

The [development setup](/docs/development-setup#choose-your-development-setup) explains how to install the current SDK or CLI. The guides use the development checkout, so an older installed release or the browser playground may expose a different API.

## Understand the boundary you are changing

A source **action** states scientific meaning, material ownership, and results. The compiler checks that meaning in the protocol, whether the work is manual or automated. Protocol documents make the work readable and shareable.

For facility planning and automation, a **method** explains how an action becomes device-neutral **procedure** tasks. A facility describes available materials and instruments; planning chooses exact resources. An **adapter** turns the allocated procedure into device files. **Runtime** executes supported reviewed files.

You only need the references relevant to your contribution. [Action contracts](/docs/language/action-contracts) explain scientific declarations; [compiler architecture](/docs/compiler/architecture) explains the ownership of each stage. [Status](/docs/status) identifies current limits, including workflow control flow and measurement results.

## Prepare the contribution for review

Each path ends with a concrete check. Include the changed source or configuration, any generated catalog or bindings it owns, the example that uses it, and the validation result. State the behavior the contribution adds and the part of the stack it exercises. A clearer protocol document, a checked scientific declaration, and a reusable method are each valuable contributions in their own right.

Keep a contribution focused enough that another scientist or engineer can reproduce it from the example. Use the [community](/community) to find collaborators for scientific domains or device knowledge that spans several paths.

## Native extensions

Rust builders and adapters are statically composed into the current CLI and Python SDK. [Extend procedure semantics](/docs/contributing/procedure-semantics#install-the-native-contribution) shows the composition point and rebuild commands. [Generate instrument files](/docs/contributing/adapters) starts from a standalone crate; [execution support](/docs/contributing/execution-support) adds runtime services separately.
