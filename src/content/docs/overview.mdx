Lab is a language for describing biology experiments precisely enough that a
compiler can check them and a laboratory, whether that's a person at a bench
or a liquid-handling robot, can carry them out. You write down what a
plasmid should be, the constraints it must satisfy before construction even
starts, and the evidence that would prove it worked. Lab checks that
description for consistency, then, once a target is chosen, turns it into
either a protocol a person can follow or a program a robot can run. A small
project usually has a few files like these.

A **design**, such as a plasmid, says what should exist and which claims
must be supported by evidence:

```lab reporter.lab
use std.bio.designs
use std.bio.golden_gate

buy part J23101
buy part B0034
buy part GFP
buy part B0015
buy backbone pSB1C3
buy restriction_enzyme BsaI:
  digest_temperature = 37 C

/** The GFP reporter under a strong constitutive promoter. */
plasmid reporter:
  sequence = dna("ACGTACGT")
  backbone = pSB1C3
  components = [J23101, B0034, GFP, B0015]
  restriction_enzyme = BsaI

  require topology == circular
  require sites(BsaI) == 0

  across 3 biological replicates

  accept sequence == design.sequence
  accept concentration >= 100 ng/uL
  accept volume >= 20 uL across 1 biological replicate
```

`plasmid` is not a keyword. It is a word `std.bio.designs` declares with
`artifact`, together with the schema every plasmid is checked against, and a
package of your own can declare words the standard library never heard of.
`across` says what a claim is believed on: three independent transformants,
not three readings of one culture.

A **workflow** says how physical materials move through a build once a
design exists. It can also react to the world instead of following a fixed
script, waking on a timer and settling into a tagged result:

```lab observe.lab
workflow grow_colonies(plate: Material<Plate>) -> ColonyGrowth:

  state observations: List<PlateObservation> = []

  when every 30 min:
    image <- capture image of plate
    colonies = detect_colonies(image)
    if colonies.isolated.count >= 8:
      return Ready{
        plate: plate,
        colonies: colonies,
        observations: observations,
      }

  when after 18 h:
    return TimedOut{plate: plate, observations: observations}
```

A plasmid can also carry a reusable **circuit**: parts composed generically,
independent of which promoter or coding sequence eventually fill it in. The
type parameters are introduced where they are first needed, and naming one
twice is what links its occurrences, so a circuit's result says which signal
it answers to and which protein it expresses.

```lab regulated-expression.lab
use std.bio.designs
use std.bio.parts

/** A promoter driving a coding sequence through a shared RBS and terminator. */
circuit regulated_expression(
  promoter: Promoter<Trigger: Signal>,
  coding: CDS<Product: Protein>,
) -> Circuit<Trigger, Product>:
  layout:
    promoter
    B0034
    coding
    B0015

tet_reporter = regulated_expression(pTet, sfGFP)
```

A **program** ties designs, policies, and workflows together into something
runnable, and reacts to what happens. This is the entry point a project
actually builds:

```lab main.lab
use std.lab.plasmid
use reporter.workflow
use reporter.observe

/** A plate reached the point where there was something worth picking. */
record ColoniesReady is Event:
  colonies: ColonyMap

workflow main() -> Material<Strain>:
  strain, plate <- build_reporter
  growth <- grow_colonies plate

  match growth:
    case Ready:
      emit ColoniesReady{colonies: growth.colonies}
      <- dispose growth.plate

    case TimedOut:
      <- dispose growth.plate

  return strain
```

You don't write instrument-specific steps anywhere in this. The compiler
figures out the rest for whichever laboratory ends up running it.

<Callout kind="note">
  **Early prototype.** Parsing, checking, and an experimental Opentrons OT-2
  backend exist today. The durable workflow runtime, the part that would
  actually run a program against a real laboratory over time, does not.
  Generated protocols must be reviewed and qualified before anyone executes
  them.
</Callout>

## How these docs are organized

**Learn Lab**, starting with [Your first program](/docs/guide/first-program),
is for writing Lab programs to describe designs and experiments. That's most
of this site, and where to start if you're new here.

Two smaller sections are for a different audience. **Toolchain** covers the
compiler's internals, useful if you're contributing to it or want to
understand how a design becomes a protocol. **Backends** covers adding
support for a new instrument. Neither is required reading to write a Lab
program.

## Where to start

[Your first program](/docs/guide/first-program) walks through a real plasmid
design end to end. If you'd rather try Lab directly, the
[playground](/playground) runs the compiler in your browser with nothing to
install.

## What exists today

The toolchain parses and checks artifact kinds, designs, generic circuits,
and workflows; verifies action contracts, material ownership, and the
evidence a claim is believed on; and includes an initial Opentrons OT-2
backend, checked against the real Opentrons simulator. Most of the standard
library is itself written in Lab. Editor support (an LSP server and a
WebAssembly API) gives a `.lab` file diagnostics, documentation on hover, and
completions like any other language. The durable workflow runtime, the part
that would execute a program continuously against a real laboratory and
react to what it observes, has not been built yet.

[Status](/docs/status) tracks exactly what's implemented, feature by
feature.
