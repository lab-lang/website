The OT-2 integration is a Lab adapter, not a compiler target. An SBOLInventory graph describes the physical OT-2 Asset and its qualified capability offerings. `lab.toml` explicitly binds that exact Asset IRI to the `opentrons.ot2` implementation. Facility allocation decides whether an offering on that Asset satisfies a reachable requirement; only then may the adapter lower work.

## Bind an installed Asset

```toml
[inventory]
document = "inventory/facility.ttl"

[[execution.adapters]]
asset = "https://example.org/my-lab/opentrons_ot2"
driver = "opentrons.ot2"
profile = "adapters/opentrons-ot2.toml"
```

The adapter declares support for the exact SBOLInventory `LiquidHandling` and `ThermalCycling` capability IRIs under `ReviewedFile` control. It provides planning and whole-program lowering, and emits standalone Opentrons Python protocols. It does not claim a Lab-managed live runtime or built-in simulation service.

The binding does not make the Asset executable by itself. Its selected offering must independently carry sufficient qualification and a compatible control mode in the inventory graph. Conversely, product metadata in RDF never causes Lab to select this driver.

## Checked implementation profile

The adapter profile describes the residual machine configuration the lowerer needs: Protocol API level, pipette models and mounts, modules, deck positions, labware, and per-stage capacity. It cannot name an Asset or another driver. Unknown fields, invalid slots, module collisions, incompatible pipettes, and capacity contradictions fail during validation.

```toml
[protocol]
api_level = "2.21"

[instruments.small]
model = "p20_single_gen2"
mount = "left"

[instruments.large]
model = "p300_single_gen2"
mount = "right"

[deck.thermocycler]
model = "thermocycler module gen2"
labware = "nest_96_wellplate_100ul_pcr_full_skirt"
capacity = 96
```

`lab adapters validate opentrons.ot2 adapters/opentrons-ot2.toml` validates the profile directly. During package planning, Lab writes its canonical form and SHA-256 into the adapter binding snapshot and reviewed plan.

## Planning and output

The implemented plasmid-build planner allocates reaction, DNA, transformation, dilution, and agar-plate wells; checks volumes and capacities; derives dependency waves from typed material flow; and projects every output from one execution plan. The maintained Python emitter is checked as ordinary Python and bundled deterministically rather than constructed as untyped string fragments.

For an allocated Asset whose readable identity is `opentrons_ot2`, output appears under:

```text
.lab/build/assets/opentrons_ot2/
├── dependency_manifest.json
├── dependency_report.pdf
├── manual_protocol.pdf
├── wave-001/
│   ├── assembly_protocol.py
│   └── manual_protocol.pdf
└── wave-002/
    ├── transformation_protocol.py
    ├── plating_protocol.py
    └── manual_protocol.pdf
```

The facility-wide `plan.execution.json` references this bundle and freezes the exact offering, Asset, adapter profile, and document digests. The directory name is derived from the Asset IRI, with a short hash only when selected Assets would otherwise collide.

## Current boundary

The adapter is experimental. Its planner covers the current Golden Gate plasmid-build vertical slice, not general liquid handling. Method, Procedure, and Capability LAIR now exist upstream, but solver extraction, `allocated-procedure`, and the immutable adapter invocation ABI are not connected, so this adapter still consumes the transitional preselected Protocol path. Lab emits the reviewed Python files but does not upload or execute them on an OT-2. Use the appropriate Opentrons application and simulator for device-side analysis, and qualify every generated protocol for the actual facility before physical use.
