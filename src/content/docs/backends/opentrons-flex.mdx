The Flex integration proves that semantic requirements and device implementation are separate. A Flex Asset can expose the same liquid-handling and thermal-cycling capability kinds as an [OT-2](/docs/backends/opentrons-ot2), while its deck, pipettes, modules, profile schema, and emitted protocol format remain entirely Flex-specific.

## Bind a Flex Asset

```toml
[[execution.adapters]]
asset = "https://example.org/my-lab/opentrons_flex"
driver = "opentrons.flex"
profile = "adapters/opentrons-flex.toml"
```

The `opentrons.flex` descriptor supports `LiquidHandling` and `ThermalCycling` under `ReviewedFile` control. It provides planning and whole-program lowering, and emits Opentrons Protocol Designer JSON. It does not provide a Lab-managed simulation or live-runtime service.

Allocation selects an exact capability offering first. The manifest binding then establishes that this compiler build has an implementation for its exact Asset. Neither manufacturer/model inference nor a CLI target flag participates.

## The profile is device-specific on purpose

A shared facility vocabulary should not flatten real implementation differences. Flex slots are `A1` through `D3`, Flex pipettes have their own model identifiers, modules have Flex-specific constraints, and trash is a movable addressable area:

```toml
[instruments.small]
model = "p50_single_flex"
mount = "left"

[instruments.large]
model = "p1000_single_flex"
mount = "right"

[deck.trash]
area = "movableTrashA3"
```

The explicit driver chooses this schema before the profile is parsed. A profile that names an OT-2 pipette, places labware beneath a thermocycler, uses a staging slot, or contains an unknown key fails before planning.

## Typed JSON emission

The emitter builds Protocol Designer schema 8 documents through a typed Rust authoring layer. Loaded labware, modules, and pipettes become typed handles; commands accept only compatible handles; embedded standard labware definitions validate well names and volumes. The resulting JSON is intended for validation with Opentrons tooling, not direct execution by Lab.

Like the OT-2 adapter, the current planner covers the plasmid-build vertical slice. Dependency waves, biological inputs, and facility allocation are shared above the adapter boundary; Flex deck allocation and JSON construction remain inside it.

## Current boundary

The adapter is experimental and provides planning plus lowering, not runtime. It still consumes the current preselected Protocol LAIR path. The accepted architecture will instead project one immutable invocation from allocated Procedure LAIR, after method choice and exact facility binding have been solved together. Generated documents require review and facility-specific qualification.
