The Byonoy Absorbance 96 demonstrates an important distinction in the facility architecture: Lab can describe an Asset, validate an explicit adapter binding, and provide a typed hardware driver before it can plan useful work for that device.

An SBOLInventory Asset may expose an `AbsorbanceMeasurement` offering under `Api` control, and `lab.toml` may explicitly bind it to `byonoy.absorbance96`. The current adapter descriptor intentionally reports `planning = false`, `lowering = false`, `simulation = false`, and `runtime = false`. Facility allocation therefore cannot mistake a compiled driver library for an executable workflow path.

## The driver boundary

The Rust driver speaks the device's raw 64-byte USB HID protocol without a vendor library. It implements a capability-oriented `PlateReader` trait rather than exposing “Byonoy” as a scientific operation. Installed wavelengths are queried from the device; whole-plate reads return 96 optical-density values in row-major order; unsupported luminescence requests are typed errors rather than fabricated values.

Those facts are implementation behavior. Facility facts remain in SBOLInventory: the exact physical Asset, location, activity, qualification, control mode, installed capability offering, and any stated wavelength parameters.

For a focused contribution, [Add execution support](/docs/contributing/execution) maps the existing loader/executor interfaces and the unfinished measurement-result boundary.

## What must land before allocation

General absorbance support needs more than adding this adapter to a registry:

1. A method definition must refine a scientific measurement intent into Procedure tasks with an `AbsorbanceMeasurement` requirement and typed material ports.
2. Capability constraints must express wavelength, plate format, read mode, and other semantic parameters using stable PropertyKind IRIs and exact units.
3. Allocated Procedure LAIR must bind that requirement to the exact offering and Asset and insert any required plate movement.
4. The adapter invocation ABI must carry the frozen read request without exposing Pliron.
5. A reviewed `lab.plate-read.v0` document and runtime executor must be completed and registered.
6. Results must become typed ExperimentalData and evidence Attachments linked to the run Activity and material lineage.

Until that complete path exists, the honest support claim is “typed driver and catalogued implementation,” not “plate-reader backend.” This fail-closed service model is how Lab can grow across the much larger EBEF capability space without presenting every recognized device as runnable.
