Facility planning answers a concrete question: **which combination of Methods, materials, and instruments can perform this experiment?** It takes the alternatives produced by refinement and selects one complete plan against a particular laboratory's inventory and policy.

A portable scientific package can be checked and refined without a facility. Producing device files also requires a facility description, suitable materials and offerings, and compatible adapter bindings. [Compiler architecture](/docs/compiler/pipeline) explains where this decision sits in the pipeline.

## Describe the laboratory

Lab reads the facility from an SBOLInventory document. The important objects are:

- A **Facility** is the laboratory selected for planning.
- **Zones** describe places within it.
- An **Asset** is a particular resource, such as an instrument or manual station.
- A **CapabilityOffering** states what that Asset can provide, including its qualification and control mode.
- A **MaterialLot** identifies physical material available for use.

A Method produces capability requirements. Planning matches those requirements to compatible offerings and checks the complete task graph. Manufacturer and model names describe equipment; the explicit adapter binding selects its implementation.

The inventory is a validated snapshot. It does not provide a live booking calendar or prove that an instrument is ready now.

## Connect a package to its facility

The manifest names the inventory document and any portable Method catalogs:

```toml lab.toml
[methods]
documents = ["methods/site-methods.json"]

[inventory]
document = "inventory/facility.ttl"
# facility = "https://example.org/my-lab/facility"
```

Lab accepts Turtle, RDF/XML, JSON-LD, and N-Triples. It validates the document as SBOL 3 and SBOLInventory Profile 0.2. If the document contains one Facility, Lab selects it automatically. With several Facilities, set `facility` to the exact absolute IRI of the one to use.

Facility objects stay in RDF. The manifest points to that description rather than duplicating its Assets and lots in TOML.

Each Method file uses `lab.method-catalog.v2`. The application composes the standard Methods with catalogs from the runnable package and its reachable path dependencies. Validation rejects incompatible signatures, malformed graphs, duplicate Method identities, unsupported versions, and catalog paths that escape their package.

[Python Method authors](/docs/toolchain/python-procedures) can generate those catalogs. Template and builder executions derive requirements from their validated Procedure programs; primitive executions state requirements directly. Declaring a capability does not supply its implementation.

## Bind instruments to adapters

To generate device files for an Asset, bind it to an installed adapter and a checked profile:

```toml lab.toml
[[execution.adapters]]
asset = "https://example.org/my-lab/opentrons_ot2"
driver = "opentrons.ot2"
profile = "adapters/opentrons-ot2.toml"
```

These three values have separate jobs. `asset` identifies the exact resource in the selected Facility. `driver` identifies the registered Lab adapter. `profile` supplies its configuration, such as deck layout, labware, and liquid-handling settings.

The profile cannot select another Asset or driver. It is validated and hashed into the plan. Runtime endpoints and credentials are supplied separately from portable project configuration. The [instrument-profile contribution path](/docs/contributing/instrument-profiles) shows how to author and check this data.

An offering's qualification and an adapter's implementation are independent. A registered adapter does not promote a merely described offering to executable. Conversely, an executable offering still needs a compatible adapter for Lab to generate and run its device representation.

## Require implementations when planning for automation

By default, `adapter-requirement` is `"optional"`. Planning can retain manual or planning-only facility bindings that have no configured adapter. A successful allocation therefore need not produce device files for every selected task.

For a project that requires an adapter for every non-manual offering, set:

```toml lab.toml
[planning]
adapter-requirement = "non-manual"
```

This requires a compatible planning adapter. Its lowering, simulation, and live-execution services still have their own contracts and readiness checks. The Golden Gate example uses this policy and explicit Method pins; it does not rely on catalog ordering.

## How the selection is made

`lab check` validates the package and its configured inventory and profiles. For a runnable package with an inventory, `lab build` and `lab plan` then use the same `lab-project` service:

1. **Refine the experiment.** Lower the entry workflow and its reachable calls, then construct compatible Method alternatives with their tasks and requirements.
2. **Assemble the problem.** Match exact design Component identities to active MaterialLots through `sbol:built`, and resolve adapter bindings against offerings on their exact Assets.
3. **Solve the complete graph.** Choose Methods, material sources, offerings, Assets, and adapters together under manifest policy. Adapter feasibility callbacks check whether configured implementations can realize the programs.
4. **Verify the allocation.** Apply the complete solution to the same compiler graph and validate its selected tasks, requirements, and material bindings.
5. **Write the reviewed bundle.** Project exact adapter invocations, lower their assigned tasks, and write the execution plan and child documents.

The solver does not select a Method merely because it appears first. No complete solution is an explained failure. Several equally valid solutions are an ambiguity unless an explicit pin or policy distinguishes them.

The orchestration is in [`lab-project/facility.rs`](https://github.com/lab-lang/lab/blob/master/crates/lab-project/src/facility.rs). Resource solving lives in [`lab-facility`](https://github.com/lab-lang/lab/tree/master/crates/lab-facility/src); bundle generation lives in [`lab-project/artifacts.rs`](https://github.com/lab-lang/lab/blob/master/crates/lab-project/src/artifacts.rs).

## Build and inspect the Golden Gate example

From a development checkout with the CLI installed:

```shell
lab check examples/golden-gate
lab build examples/golden-gate
lab run examples/golden-gate/.lab/build --dry-run
```

The example declares a Facility, exact input lots, a manual workstation, and an OT-2 with plannable liquid-handling and thermal-cycling offerings. Its manifest pins temperature-staged Golden Gate assembly and automated transformation, recovery, and antibiotic selection. Provisioning and disposal use manual Methods.

The dry-run checks and narrates the reviewed plan without executing hardware. For this example it reports that the plan is neither live-executable nor simulatable through Lab. The offerings are `Plannable`, and Lab exports Opentrons files for vendor tooling rather than providing an Opentrons executor. Successful document validation does not imply readiness to run.

`lab build` writes portable artifacts and the facility bundle under `.lab/build/`. `lab plan` writes just the facility bundle under `.lab/plan/`; with `--program <name>`, its default becomes `.lab/plan/<name>/`. The CLI reports the actual output paths.

The build keeps the evidence for each major decision:

```text
.lab/build/
├── compiler/
│   ├── refined.lair
│   ├── planning-problem.json
│   ├── facility-solution.json
│   ├── allocated.lair
│   └── adapter-invocations.json
├── adapter_bindings.json
├── facility_lowering.json
├── plan.execution.json
└── assets/
    └── opentrons_ot2/
        └── tasks/
```

Under `tasks/`, each supported allocated task has its generated protocol, invocation manifest, and operator document. Directories such as `001-pipetting-program/` and `002-thermal-program/` reflect physical programs, not a fixed list of biological operations. The pinned transformation, recovery, dilution, and selection Methods also produce supported pipetting or thermal tasks. Manual provisioning and disposal remain explicit nodes in the plan.

To understand a result, compare `planning-problem.json` with `facility-solution.json`: the first contains the available alternatives and requirements; the second records the choices. `allocated.lair` is the compiler's verified application of those choices. `adapter-invocations.json` records the work handed to each adapter.

## Review and execution

The execution plan freezes the selected Facility, Methods, lots, offerings, Assets, and adapter profiles. It also records the dependency graph and digests of inventory, compiler evidence, and child documents. Runtime checks that complete set of references before an executor can touch hardware.

Resume is tied to the same reviewed inputs. Changed plan content, profiles, evidence, or child documents invalidates it. A resource substitution requires a newly reviewed plan; runtime does not query inventory for an alternative instrument.

On completion, Lab writes a new inventory result document with run Activities, resource and input-lot Usages, output lots, lineage, and evidence attachments. The source inventory is preserved. General instrument results feeding workflow acceptance decisions are still an open integration boundary.

## What allocation does not yet solve

A selected material dependency says which task supplies material to another. It does not automatically propagate physical well locations or liquid-class assignments between independently emitted files. Those tasks still need explicit staging.

Lab also has no general reservation service, calendar, queue, consumable depletion model, dynamic rescheduling, or complete movement optimizer. The reviewed dependency graph is a foundation for coordination; it does not claim those services already exist.

## Scaling to a larger facility

The EBEF example models Caltech's Ecology and Biosphere Engineering Facility using nested Zones, installed Assets, and capability offerings. Public equipment information stays at `Described` with `UnspecifiedControl`, because it does not establish an operational control path.

A separate synthetic extension exercises multi-Asset simulation with explicit reviewed documents:

```shell
cargo test --locked -p lab-runtime --test ebef_acceptance
```

That test exercises runtime composition. It does not establish source-to-device compiler lowering for the whole EBEF catalog. The architectural aim is to add incubators, readers, microscopes, storage, and other resources through the same offering and contract boundaries, with the corresponding Methods, adapters, and evidence in place. [Status](/docs/status) tracks the current coverage.
