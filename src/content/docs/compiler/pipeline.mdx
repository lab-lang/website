Lab is a multi-layer compiler. It does not translate an experiment directly into one robot script, and a device is not selected by a command-line target flag. The compiler preserves scientific meaning while it progressively commits to methods, physical resources, and implementation details.

```text
Lab or Python source
    -> checked portable module IR
    -> LAIR design and intent
    -> method alternatives with procedure and capability requirements
    -> graph-wide method and facility solving
    -> allocated procedure LAIR
    -> asset-bound adapter invocations
    -> reviewed execution plan and device documents
    -> run ledger, material lineage, and evidence
```

Much of this path is implemented, but it is not yet connected as one canonical pipeline. Both frontends reach one checked module model. `PortableLairProgram::refine_methods` now consumes a validated, facility-independent `lab-method` registry and produces verifier-valid `refined-alternatives` LAIR containing compatible Method candidates, Procedure dataflow, exact parameters, and first-class Capability requirements. Separately, the current package path validates SBOLInventory facility graphs, allocates its transitional reachable requirements to exact offerings and Assets, emits asset-specific bundles through compatible adapters, and validates a reviewed plan before simulation or supported live execution. Global problem extraction, joint method/facility solving, solution application, and CLI uptake are the missing bridge; until they land, `lab build` still selects the plasmid-build Protocol before allocation and emits the v2 checked-module requirement projection.

## The layers and their owners

| Layer                      | Representation                                  | Owns                                                                                                                                      |
| -------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Source                     | Lab or Python                                   | The experiment as an author writes it                                                                                                     |
| Portable frontend boundary | `CheckedModule`                                 | Resolved symbols, types, action contracts, biological identities, and affine material ownership                                           |
| Transforming compiler IR   | LAIR on Pliron                                  | Design intent, typed material flow, method alternatives, procedures, capability requirements, and eventually exact allocation annotations |
| Constraint problem         | Compiler-owned solver model                     | Joint choices over methods, offerings, Assets, adapters, MaterialLots, movement, capacity, and scheduling                                 |
| Facility snapshot          | Validated SBOLInventory                         | Facilities, Zones, Assets, capability offerings, qualification, control modes, parameters, and MaterialLots                               |
| Adapter invocation         | Versioned immutable record                      | The exact allocated Asset, implementation, checked profile, inputs, outputs, and device-level work to lower                               |
| Runtime ABI                | Reviewed execution plan and child run documents | Frozen identities and digests approved for execution                                                                                      |
| Operational record         | Ledger and output SBOLInventory document        | What ran, material changes, provenance, and evidence                                                                                      |

SBOLInventory is the target-environment description, but it is not another LAIR dialect. The compiler queries an immutable validated snapshot and brings only selected identities and the inventory digest into the allocated program. Facility RDF never becomes compiler IR, and Lab does not maintain a parallel inventory TOML model.

## Method selection and facility allocation are one decision

A source action states scientific intent. It should not permanently own one instrument capability. A method refines that intent into a procedure: a primitive service may require one capability, while a composite method may require liquid handling, thermal cycling, transport, incubation, and measurement as several related tasks.

Method refinement is facility-independent: the compiler can enumerate scientifically valid candidates without knowing where the experiment will run. Selecting an unpinned method is facility-dependent. The solver must choose a method together with exact capability offerings, Assets, adapters, material lots, movement, and scheduling. If two complete solutions remain equally valid under the stated policy, planning reports the ambiguity instead of silently taking the first.

This distinction prevents two common architecture mistakes: hard-coding Golden Gate or one robot into the source action, and choosing a method before discovering that another method is the only one the selected facility can actually realize.

## LAIR and Pliron

LAIR is the mutable, verifier-rich middle of the compiler. Pliron provides operations, SSA values, regions, analyses, rewrite infrastructure, textual IR, and pass pipelines. Pliron is deliberately internal: adapters and Python extensions exchange compiler-owned immutable records rather than Pliron contexts, pointers, or lifetimes.

The intended executable LAIR stages are:

```text
design-intent
    -> refined-alternatives
    -> allocated-procedure
```

`design-intent` contains reachable design facts and method-neutral work. `refined-alternatives` contains candidate method regions with Procedure tasks and first-class Capability requirements. A read-only analysis extracts the global constraint problem. The allocation pass applies one complete solution back to the exact LAIR identities, removes unselected candidates, inserts explicit movement, and produces `allocated-procedure`. No adapter may consume unresolved alternatives.

The compiler now represents both `design-intent` and `refined-alternatives`. Design and Workflow operations form the current source-lowering boundary; Method, Procedure, and Capability operations represent every applicable candidate after refinement. The older Protocol dialect still powers current device backends through a fixed pre-facility conversion while solver extraction and `allocated-procedure` are built. That transitional Protocol path is being replaced rather than generalized.

## Stable boundaries around the mutable IR

The compiler can rewrite LAIR aggressively because its external boundaries are ordinary versioned data:

- Frontends produce `CheckedModule`.
- Facility ingestion produces an immutable validated inventory snapshot.
- Solvers return decisions keyed by stable method, requirement, procedure-node, and material-input identities.
- Adapters consume immutable invocation records and emit reviewed child documents.
- Runtime consumes `lab.execution-plan.v1`; it never runs compiler passes or reallocates resources.

That is why Lab remains a compiler rather than becoming a workflow engine built around device plugins. The compiler makes and verifies decisions; adapters realize already-allocated work; runtime executes exactly what was reviewed.
