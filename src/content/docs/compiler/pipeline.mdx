The pipeline is one idea applied repeatedly: take a description of what
should exist and make it progressively more concrete until something in the
world can act on it. A `.lab` file describes a **design**: an artifact, the
constraints it must satisfy, the evidence that would prove it worked.
Lowering restates that design as a **workflow**: the materials that must
move through a build for the artifact to exist, with no opinion yet about
who or what performs any step. Selecting a target turns the workflow into a
**protocol**: the same build committed to concrete methods on a specific
instrument. A backend then turns the protocol into its runnable forms: a
typeset document a person follows at the bench, a program a robot runs, or
both from the same compilation.

Each of those transitions is a stage with a name you can ask for on the
command line, so specialization decisions stay visible rather than implied
by a library default.

| Stage   | Produces                   | What happens                                                                                                                                                                                    |
| ------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Parse   | Spanned source AST         | Surface syntax becomes a tree with byte offsets attached, for diagnostics.                                                                                                                      |
| Check   | `CheckedModule`            | Imports resolve, types check, action contracts resolve, and affine material flow is verified. This is the portable source-compilation boundary: the last point that knows source syntax at all. |
| Lower   | `PortableLairProgram`      | The checked module becomes LAIR, the Lab Automation Intermediate Representation: a Design layer for artifact intent, a Workflow layer for target-neutral realization.                           |
| Select  | `ProtocolLairProgram`      | Workflow operations are replaced by Protocol operations and fully eliminated. Material linearity is re-verified at this mandatory backend boundary.                                             |
| Compile | A backend's `Program` type | A backend consumes verified Protocol operations and plans an execution: for either Opentrons bench, deck, well, and labware allocation.                                                         |
| Emit    | `ArtifactBundle`           | The backend's plan becomes files: generated Python for a robot, and a typeset PDF protocol for a person, rendered through Typst from the same plan.                                             |

## Two boundaries worth knowing by name

`CheckedModule` is the portable frontend boundary. Everything before it knows
source syntax; nothing after it does. `lab-compiler` never re-parses source
outside one file, `source_lowering.rs`, whose entire job is reading
`CheckedModule` and nothing else.

`ProtocolLairProgram` is the mandatory backend boundary. No backend receives
anything less specialized than this: by the time a backend sees a program,
every workflow operation has already been replaced by a protocol operation,
and material linearity has already been checked twice: once when Workflow
LAIR verifies, and again after Protocol selection.

## One boundary, two frontends

The frontend boundary is what makes the compiler's inputs plural.
Everything downstream of `CheckedModule`, which is LAIR, its verification,
target selection, and every backend, neither knows nor cares what syntax the
module was written in. Any frontend that produces a `CheckedModule` inherits
the whole pipeline.

Two frontends target that boundary. Python is where most experiments are
written, because it is the language a laboratory already has code in. Lab is
the native language, and the one the checker's vocabulary is built around.
Both produce the same `CheckedModule`, so neither is a wrapper over the
other and nothing downstream can tell them apart.

SBOL is not a third frontend. It is the vocabulary designs are exchanged in,
and both frontends speak it: the type system grounds parts and roles in the
ontologies SBOL names, and the Python frontend builds on the tools already
written against SBOL, which are pySBOL3 for designs and LOICA for circuits.
So a design can arrive from a registry and leave for one without SBOL being
a separate way into the compiler.

## Stage names, concretely

LAIR itself moves through three named stages, and mixing operations from two
non-adjacent stages in the same module is rejected outright:

- `Design`: artifact intent only (`design.plasmid` and similar).
- `DesignWorkflow`: Design plus target-neutral Workflow operations
  (`workflow.realize`, `workflow.provision`, and so on).
- `TargetSelectedProtocol`: Design plus Protocol operations. Workflow
  operations must be completely gone by this point; a module holding both
  Workflow and Protocol operations at once fails to verify.

You can ask for the intermediate representation directly at almost any of
these points with `labc --emit`:

```shell
labc reporter.lab --emit source-ast
labc reporter.lab --emit module-ir
```

See [CLI reference](/docs/compiler/cli-reference) for the full table of
`--emit` targets, and [LAIR dialects](/docs/compiler/lair-dialects) for what
the Design, Workflow, and Protocol operations actually look like.
