Each stage has a name you can ask for on the command line, so specialization
decisions stay visible rather than implied by a library default.

| Stage   | Produces                   | What happens                                                                                                                                                                                    |
| ------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Parse   | Spanned source AST         | Surface syntax becomes a tree with byte offsets attached, for diagnostics.                                                                                                                      |
| Check   | `CheckedModule`            | Imports resolve, types check, action contracts resolve, and affine material flow is verified. This is the portable source-compilation boundary: the last point that knows source syntax at all. |
| Lower   | `PortableLairProgram`      | The checked module becomes LAIR: a Design layer for artifact intent, a Workflow layer for target-neutral realization.                                                                           |
| Select  | `ProtocolLairProgram`      | Workflow operations are replaced by Protocol operations and fully eliminated. Material linearity is re-verified at this mandatory backend boundary.                                             |
| Compile | A backend's `Program` type | A backend consumes verified Protocol operations and plans an execution: for either Opentrons bench, deck, well, and labware allocation.                                                         |
| Emit    | `ArtifactBundle`           | The backend's plan becomes files: generated Python for a robot, or a manual protocol for a person.                                                                                              |

## Two boundaries worth knowing by name

`CheckedModule` is the portable frontend boundary. Everything before it knows
source syntax; nothing after it does. `lab-compiler` never re-parses source
outside one file, `source_lowering.rs`, whose entire job is reading
`CheckedModule` and nothing else.

`ProtocolLairProgram` is the mandatory backend boundary. No backend receives
anything less specialized than this: by the time a backend sees a program,
every workflow operation has already been replaced by a protocol operation,
and material linearity has already been checked twice: once when Workflow
LAIR verifies, and again after Protocol selection.

## Stage names, concretely

LAIR itself moves through three named stages, and mixing operations from two
non-adjacent stages in the same module is rejected outright:

- `Design`: artifact intent only (`design.plasmid` and similar).
- `DesignWorkflow`: Design plus target-neutral Workflow operations
  (`workflow.realize`, `workflow.provision`, and so on).
- `TargetSelectedProtocol`: Design plus Protocol operations. Workflow
  operations must be completely gone by this point; a module holding both
  Workflow and Protocol operations at once fails to verify.

You can ask for the intermediate representation directly at almost any of
these points with `labc --emit`:

```shell
labc reporter.lab --emit source-ast
labc reporter.lab --emit module-ir
```

See [CLI reference](/docs/compiler/cli-reference) for the full table of
`--emit` targets, and [LAIR dialects](/docs/compiler/lair-dialects) for what
the Design, Workflow, and Protocol operations actually look like.
