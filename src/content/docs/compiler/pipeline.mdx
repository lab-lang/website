Lab is a multi-layer compiler. It does not translate an experiment directly into one robot script, and a device is not selected by a command-line target flag. The compiler preserves scientific meaning while progressively committing to Methods, physical resources, and implementation details.

```text
Lab or Python source
    -> checked portable module IR
    -> LAIR Design and Intent
    -> Method alternatives with Procedure and Capability graphs
    -> graph-wide Method and facility solving
    -> Allocated Procedure LAIR
    -> Asset-bound adapter invocations
    -> reviewed execution plan and device documents
    -> run ledger, material lineage, and evidence
```

This is one connected production path. Both frontends reach the same checked module model. The shared project service composes the compiler's standard Methods with versioned catalogs contributed by the runnable package and its reachable dependencies, validates one facility-independent registry, lowers all checked program modules into `design-intent`, projects one global planning problem, solves Method and resource choices together, applies the complete solution to produce `allocated-procedure`, and projects immutable exact-task adapter invocations. `lab build`, `lab plan`, and Python facility planning all call that service.

The former fixed Protocol dialect, pre-facility Golden Gate selector, checked-module requirement reconstruction, and whole-program device lowering path have been removed.

## The layers and their owners

| Layer                      | Representation                              | Owns                                                                                                                  |
| -------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Source                     | Lab or Python                               | The experiment as an author writes it                                                                                 |
| Portable frontend boundary | `CheckedModule`                             | Resolved symbols, types, action contracts, biological identities, and affine material ownership                       |
| Transforming compiler IR   | LAIR on Pliron                              | Design and Intent, Method alternatives, Procedure dataflow, Capability requirements, and exact allocation annotations |
| Constraint problem         | `lab.planning-problem.v4`                   | Joint choices over Methods, offerings, Assets, adapters, MaterialLots, dependencies, and policy                       |
| Facility snapshot          | Validated SBOLInventory                     | Facilities, Zones, Assets, capability offerings, qualification, control modes, parameters, and MaterialLots           |
| Facility solution          | `lab.facility-planning-solution.v2`         | One complete selection keyed to the exact planning identities                                                         |
| Allocated work             | `allocated-procedure` LAIR                  | The selected Method graph with exact requirement and material bindings                                                |
| Adapter invocation         | `lab.adapter-invocations.v5`                | Exact selected tasks grouped by Asset and adapter, with all compiler and inventory digests                            |
| Runtime ABI                | `lab.execution-plan.v5` and child documents | Frozen identities and digests approved for execution                                                                  |
| Operational record         | Ledger and output SBOLInventory document    | What ran, material changes, provenance, and evidence                                                                  |

SBOLInventory is the target-environment description, but it is not another LAIR dialect. The compiler queries an immutable validated snapshot and carries only selected identities and the inventory digest into the allocated program. Facility RDF never becomes compiler IR, and Lab does not maintain a parallel inventory TOML model.

## Method selection and facility allocation are one decision

A source action states scientific intent. It does not permanently own one instrument capability. A Method refines that intent into a Procedure: a primitive service may require one capability, while a composite Method may require liquid handling, thermal cycling, transport, incubation, and measurement as several related tasks.

Method refinement is facility-independent: the compiler can enumerate scientifically valid candidates without knowing where the experiment will run. Selecting an unpinned Method is facility-dependent. The solver chooses it together with exact capability offerings, Assets, adapters, material lots, and dependencies. If two complete solutions remain equally valid under the stated policy, planning reports the ambiguity instead of silently taking the first.

Persistent Method extension does not require a compiler fork. A package names one or more `lab.method-catalog.v1` JSON documents under `[methods]`; Python's typed `MethodCatalog.write` API emits the same contract. The records contain open semantic IRIs and ordinary typed graphs rather than Pliron objects. Project loading validates each document, composes reachable dependency catalogs in deterministic order, and validates the combined registry again before constructing LAIR.

The built-in Golden Gate Method shows why this matters. Reaction setup requires liquid handling, thermal cycling is a separate Procedure task with its own requirement, and a typed material edge connects them. One facility may allocate both to one OT-2; another may allocate setup to a STAR and cycling to an ODTC. The source experiment is unchanged.

## LAIR and Pliron

LAIR is the mutable, verifier-rich middle of the compiler. Pliron supplies operations, SSA values, regions, analyses, rewrite infrastructure, textual IR, and pass pipelines. Pliron remains internal: adapters and Python extensions exchange compiler-owned immutable records rather than contexts, pointers, or lifetimes.

```text
design-intent
    -> refined-alternatives
    -> allocated-procedure
```

`design-intent` contains reachable design facts and method-neutral work. `refined-alternatives` contains candidate Method regions with Procedure tasks and first-class Capability requirements. A read-only analysis extracts the constraint problem. The allocation pass applies one complete solution back to the exact LAIR identities, removes unselected candidates, and produces `allocated-procedure`. No adapter can consume unresolved alternatives.

## Stable boundaries around mutable IR

The compiler can rewrite LAIR aggressively because its external boundaries are ordinary versioned data:

- Frontends produce `CheckedModule`.
- Facility ingestion produces an immutable validated inventory snapshot.
- The solver returns decisions keyed by stable Method, Requirement, Procedure-task, and material-input identities.
- Allocation must revalidate and apply the complete solution to the exact source problem.
- Adapters consume immutable invocation records and emit reviewed child documents.
- Runtime consumes `lab.execution-plan.v5`; it never runs compiler passes or reallocates resources.

Each built-in automation adapter receives only the tasks and requirements assigned to one exact Asset invocation. Shared Procedure views validate operation IRIs, parameters, canonical units, material roles, Capability kinds, and exact allocation ownership before device-specific planning begins. Unsupported semantics fail explicitly.

That is why Lab remains a compiler rather than a workflow engine organized around device plugins. The compiler makes and verifies decisions; adapters realize already allocated work; runtime executes exactly what was reviewed.
