`lab` is the package and facility CLI. `labc` inspects one source file. `lab-opt` parses and transforms textual LAIR. All `lab` commands accept the global `--json` flag, including after the subcommand.

## `lab`

| Command                                               | Does                                                                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `lab new <path> [--name <name>]`                      | Creates a package with `lab.toml` and `src/programs/main.lab`.                                                                       |
| `lab check [<path>]`                                  | Checks a source file or package and validates configured inventory and adapter bindings.                                             |
| `lab build [<path>] [--out-dir <dir>]`                | Writes portable compiler artifacts and, when configured, facility allocation, reviewed plans, and adapter bundles.                   |
| `lab plan [<path>] [--out-dir <dir>]`                 | Writes only the facility plan and allocated adapter lowerings.                                                                       |
| `lab adapters describe [--driver <id>]`               | Prints the adapter catalog or one descriptor, including semantic capabilities, control modes, formats, services, and profile schema. |
| `lab adapters default <driver> [--name <name>]`       | Prints one adapter's complete canonical reference profile.                                                                           |
| `lab adapters validate <driver> <profile>`            | Parses and semantically validates a profile against an explicit driver.                                                              |
| `lab adapters render <driver> <profile>`              | Prints the canonical validated profile.                                                                                              |
| `lab run <plan-dir> --dry-run`                        | Validates the reviewed plan and prints the complete execution without touching hardware.                                             |
| `lab run <plan-dir> --simulate`                       | Executes through configured simulation adapters.                                                                                     |
| `lab run <plan-dir> [--asset-endpoint <IRI=address>]` | Executes supported live adapters after full preflight and confirmation.                                                              |
| `lab metadata [<path>]`                               | Prints the resolved manifest and module list.                                                                                        |
| `lab update [--check]`                                | Checks for or installs a newer `lab`, `labc`, and `lab-opt` release.                                                                 |

`lab build` defaults to `.lab/build`; `lab plan` defaults to `.lab/plan`. Relative `--out-dir` values are resolved from the project root. There is no `--target`, `--no-target`, or `[target]` table: the selected SBOLInventory Facility and its explicitly bound Assets determine eligible adapter lowerings.

The runtime options are:

- `--dry-run` validates and narrates without executing.
- `--simulate` selects simulation execution and conflicts with `--dry-run`.
- `--yes` skips only the initial confirmation; manual steps and physical handoffs still require the operator.
- `--resume` continues the exact reviewed plan from its durable ledger and rejects digest changes.
- `--asset-endpoint <ASSET_IRI=ADDRESS>` supplies a repeatable non-portable endpoint for a networked Asset.

## Typical facility workflow

```shell
lab check examples/golden-gate
lab adapters describe --driver opentrons.ot2
lab build examples/golden-gate
lab run examples/golden-gate/.lab/build --dry-run
```

Use `lab plan` instead of `lab build` when only the reviewed facility bundle is needed:

```shell
lab plan examples/ebef/acceptance
lab run examples/ebef/acceptance/.lab/plan --simulate
```

## `labc`

```shell
labc <source.lab> --emit <target> [--output-dir <dir>] [--inventory <file.json>]
```

`labc` remains a single-file compiler-inspection tool. Its `--inventory` option is the legacy symbolic JSON build inventory used by the direct OT-2 concept-spike emits; it is not the package SBOLInventory interface. Use `lab check`, `lab build`, and `lab plan` for current package and facility behavior.

| `--emit` value             | Produces                                       |
| -------------------------- | ---------------------------------------------- |
| `human`                    | A readable summary of the checked module.      |
| `source-ast`               | The spanned source AST as JSON.                |
| `module-ir`                | The checked portable module as JSON.           |
| `automation-json`          | The direct OT-2 execution-plan projection.     |
| `manual-protocol`          | A Markdown protocol.                           |
| `opentrons-assembly`       | Generated OT-2 assembly Python.                |
| `opentrons-transformation` | Generated OT-2 transformation Python.          |
| `opentrons-plating`        | Generated OT-2 plating Python.                 |
| `automation-bundle`        | The direct OT-2 artifacts together.            |
| `dependency-plan`          | The legacy symbolic-inventory dependency plan. |
| `full-build-bundle`        | The legacy direct OT-2 build bundle.           |

## `lab-opt`

```shell
lab-opt [<input>] --pass-pipeline "builtin.module(protocol-check-material-linearity)"
```

`lab-opt` reads textual Pliron IR from a file or standard input and runs a module-anchored pass pipeline. `--input-stage` requires the input to satisfy a named `IrStage`; `--verify-each` verifies before and after every pass; `--print-before-all` and `--print-after-all` write snapshots to `--ir-printing-dir`; and `--list-passes` prints the registered passes.

The textual tool exposes Design, Workflow, Method, Procedure, Capability, and Protocol operations and verifies the implemented `design-intent`, `refined-alternatives`, and transitional `method-selected-protocol` stage contracts described in [LAIR dialects](/docs/compiler/lair-dialects). Source-to-method refinement is currently a `lab-compiler` API rather than a registered `lab-opt` pass. Solver passes and the `allocated-procedure` stage are not yet implemented, and the package CLI still uses the transitional Protocol path.
