LAIR, the Lab Automation Intermediate Representation, is a family of Pliron dialects inside `lab-compiler`. It preserves biological meaning, typed physical materials, source ancestry, Method alternatives, Capability requirements, and exact allocation while the compiler moves from scientific intent to executable Procedure tasks.

LAIR is not the serialized execution plan, the SBOLInventory graph, or the adapter API. Those representations have different lifecycles: LAIR is mutable compiler state; the facility graph is an immutable query input; planning records, adapter invocations, and reviewed plans are versioned immutable projections.

## Implemented dialects

- Design represents reusable DNA sequences, plasmids, strains, and declarative biological identity.
- Workflow represents method-neutral realization, provision, transformation, recovery, dilution, and plating with typed material use-def edges.
- Method owns compatible candidate regions for one exact Intent operation.
- Procedure represents open semantic task and material-state IRIs, typed SSA dataflow, exact parameters, and material inputs.
- Capability represents exact requirement and property-constraint IRIs, qualification floors, and accepted control modes.
- Allocation records the selected Method and exact offering, Asset, adapter, and MaterialLot bindings.
- Meta records an explicit stage contract on the module.

The Procedure dialect uses a small closed structural vocabulary and open semantic operation IRIs. Adding a centrifugation, imaging, chromatography, or culture Method should normally add declarative Method records and semantic identities, not a new Rust operation class for every laboratory verb.

## Canonical stages

The production pipeline has three verifier-valid LAIR boundaries:

```text
design-intent
    -> refined-alternatives
    -> allocated-procedure
```

`design-intent` contains Design values and method-neutral Workflow/Intent operations. `PortableLairProgram` owns the Pliron context and module for this stage.

`refined-alternatives` eliminates every supported refinable Intent action in favor of `method.choice` regions. Each candidate contains verifier-valid Procedure dataflow and first-class Capability requirements, and all candidates for one choice yield a compatible typed signature. The bundled registry covers every Intent in the current Golden Gate slice and retains real alternatives for artifact realization and culture recovery.

A read-only analysis projects `lab.planning-problem.v4` from the refined graph. One solver selects Methods, exact MaterialLots, CapabilityOfferings, Assets, adapters, and dependencies together. The solver does not mutate LAIR, and candidate order is never allocation.

The allocation pass validates the complete solution against the exact problem and applies it back to the same stable identities. `allocated-procedure` contains one selected Method for every choice, every selected task and parameter, one exact binding for every Capability requirement, one exact source for every material input, and one context naming the Facility and inventory digest. It contains no unresolved Method choice or Workflow action.

Operation verifiers establish local type and attribute invariants. Stage verification establishes graph completeness and identity relationships. `MaterialLinearityAnalysis` checks whole-module affine material use over the final selected SSA graph before adapter invocation projection.

The former fixed Protocol dialect and `method-selected-protocol` stage have been removed. They are not a compatibility path for new adapters.

## Capability requirements live in LAIR

Capability requirements are first-class operations produced by Method refinement. They carry a stable identity, semantic capability-kind IRI, minimum qualification, accepted control modes, typed property constraints, owning Procedure task, and ancestry back to the Method and source action.

There is one authoritative requirement graph. The planner does not traverse `CheckedModule` to rediscover a parallel collection of strings. Allocation decisions are keyed back to the exact LAIR identities from which the problem was projected.

## Planning is not another dialect

The global planning problem is an owned serializable constraint representation suited to whole-graph solving. It carries stable Method choices, Procedure tasks, requirements, parameters, materials, and ancestry without Pliron pointers. The solver combines it with a validated immutable SBOLInventory snapshot, exact MaterialLot evidence, configured adapter bindings, and explicit manifest policy.

SBOLInventory is the target-environment description, not a LAIR dialect. Facility, Zone, Asset, CapabilityOffering, and MaterialLot remain RDF objects. Allocated LAIR carries only exact selected IRIs and provenance digests.

## The device boundary

`lab.adapter-invocations.v5` is projected only from verifier-valid Allocated Procedure LAIR. It freezes the selected Method graphs, exact tasks, typed parameters and ports, material sources, requirement-to-offering-to-Asset bindings, adapter profiles, and inventory and compiler-evidence digests.

Invocations group only the tasks and requirements allocated to one exact Asset and adapter. OT-2, Flex, and STAR lower those assigned tasks today. A backend cannot inspect checked source, unresolved candidates, facility RDF, or another Asset's work. Each independently executable child document names the exact Requirement it realizes.

## Why Pliron stays internal

Pliron is the right substrate for transformations but the wrong public ABI. Rust adapters, Python extensions, solvers, and runtimes should not depend on a compiler context being alive or manipulate raw IR pointers. Public surfaces are compiler-owned records with schema versions and validation:

- portable Method definitions and Capability contracts;
- planning problems and complete facility solutions;
- immutable adapter descriptors and invocations; and
- reviewed execution plans and child run documents.

A built-in adapter may introduce a private dialect when device planning benefits from dataflow, rewriting, or verification. That remains behind the adapter boundary; an external consumer can use the same versioned invocation contract without linking Pliron.
