LAIR, the Lab Automation Intermediate Representation, is a family of Pliron dialects inside `lab-compiler`. It preserves biological meaning, typed physical materials, source ancestry, requirements, and eventually allocation while the compiler moves from scientific intent to executable procedure.

LAIR is not the serialized execution plan, the SBOLInventory graph, or the adapter API. Those representations have different lifecycles: LAIR is mutable compiler state; the facility graph is an immutable query input; adapter invocations and reviewed plans are versioned immutable projections.

## What exists today

The implemented vertical slice has three dialects:

- Design represents declarative plasmid artifact intent.
- Workflow represents target-neutral realization, provision, transformation, recovery, dilution, and plating with typed material use-def edges.
- Protocol represents one method-selected plasmid-building procedure and its richer material and evidence types.

The current conversion expands `workflow.realize` into synthesis and Golden Gate assembly, converts the remaining supported workflow operations, rewrites uses to the new results, and eliminates the original Workflow operations. `MaterialLinearityAnalysis` then verifies whole-module affine material ownership. `lab-opt` can parse textual LAIR and run the registered `protocol-check-material-linearity` pass.

This proves the mechanics Lab needs: typed operations, SSA material flow, operation verification, whole-module analysis, dialect conversion, textual round trips, and compiler-owned pass pipelines. It does not yet express the full architecture. In particular, selecting Golden Gate before looking at a facility and separately reconstructing capability requirements from checked actions are transitional shortcuts.

## The accepted dialect organization

The next architecture separates the questions the compiler must answer:

| Concern           | Dialect or representation                       | Question                                                                                      |
| ----------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Design            | Design dialect                                  | What biological object and evidence should exist?                                             |
| Intent            | Intent dialect                                  | What scientifically meaningful action is requested, with what typed materials?                |
| Method choice     | Method dialect with candidate regions           | Which scientifically valid procedures could realize that intent?                              |
| Procedure         | Procedure dialect                               | What ordered or data-dependent tasks and material transformations does a candidate contain?   |
| Capability        | Capability dialect                              | What semantic services and typed property constraints does each procedure task require?       |
| Global allocation | Purpose-built constraint model                  | Which method, offering, Asset, adapter, lot, movement, and schedule form a complete solution? |
| Allocated work    | Allocated Procedure LAIR                        | Which exact solution was selected and is ready for adapter projection?                        |
| Device planning   | Adapter-local model, optionally another dialect | How does one allocated invocation become a valid device document?                             |

The Procedure dialect uses a small closed structural vocabulary and open semantic operation IRIs. Adding a centrifugation, imaging, chromatography, or culture method should normally add declarative method records and semantic identities, not a new Rust operation class for every laboratory verb.

## Candidate regions

One intent operation may refine to several candidate regions. Each region must consume and yield compatible material and information types, and each contains all Procedure and Capability operations required by that method. A primitive remote or manual service may be one task and one requirement. A composite method may contain many tasks and explicit transport between them.

Refinement enumerates candidates but does not pick among them. A source or manifest method pin constrains the choice. Otherwise one graph-wide solver selects the method together with facility resources. This is essential because method feasibility depends on the complete facility, not just whether one instrument advertises one capability.

## Capability requirements live in LAIR

Capability requirements are first-class operations produced by method refinement. They carry a stable requirement identity, semantic capability-kind IRI, minimum qualification, accepted control modes, typed property constraints, material ports, and ancestry back to the method and source action.

There is one authoritative requirement graph. The planner must not independently traverse `CheckedModule` to rediscover a similar set of strings. A read-only LAIR analysis projects requirements into the solver model; allocation decisions are keyed back to those same identities and applied to the same module.

## Stage contracts

The intended stages are verifier contracts, not labels inferred from whichever operation happens to appear:

```text
design-intent
refined-alternatives
allocated-procedure
```

Operation verifiers establish local type and attribute invariants. Analyses establish graph-wide invariants such as affine material use, candidate contract equivalence, requirement completeness, and allocation consistency. Every transformation accepts one verified stage and returns another verified stage or an error.

`allocated-procedure` contains no unresolved method choice. Every executable requirement records an exact `Requirement -> CapabilityOffering -> Asset` binding and, where execution is requested, an explicit compatible adapter binding. Exact MaterialLot inputs and explicit movement nodes are part of the same allocation result.

## Why Pliron stays internal

Pliron is the right substrate for transformations but the wrong public ABI. Rust adapters, Python adapters, solvers, and runtimes should not depend on a compiler context being alive or manipulate raw IR pointers. The public surfaces are compiler-owned records with schema versions and validation:

- method definitions and capability contracts;
- solver problems and solutions;
- adapter descriptors and invocations;
- reviewed execution plans and child run documents.

A built-in adapter may introduce its own Pliron dialect when device planning benefits from dataflow, rewriting, or verification. That is still behind the adapter boundary; an external adapter can implement the same versioned invocation contract without linking Pliron.
