**Execution support** connects a reviewed instrument document to the code that carries it out. Choose this path when Lab can produce the instructions and you want `lab run` to operate the device and record progress, completion, or failure.

For example, a thermocycler adapter can describe the temperature steps to perform. Its live executor uses a device driver to send those steps to the cycler, observe completion, and report an error if communication fails. A simulator can exercise the same document without operating hardware; simulation and live execution are registered separately.

You contribute a loader that validates the document, a simulator or live executor, and focused examples of success and failure. Reuse the instrument's driver or vendor SDK where possible. Add missing command encoding or transport in the driver repository; connect it to reviewed Lab documents through the executor.

## Decide whether Lab needs to run the device

If you plan to load generated files into vendor software and run them there, file generation may be all you need. The current Opentrons integrations work this way. Add execution support when running through Lab would give you the progress and run records you need.

If Lab cannot yet generate the instructions, start with [the adapter guide](/docs/contributing/adapters). If only supported operating settings differ, use [an instrument profile](/docs/contributing/instrument-profiles). Scientific method selection and facility allocation happen before an executor receives the reviewed work.

Returning measurements into a scientific workflow is further work: a driver returning readings does not by itself connect those readings to Lab's acceptance claims. The [measurement boundary below](#understand-the-measurement-gap) explains what remains to be implemented.

## Find the code you own

| Layer                        | Contribution                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------ |
| Instrument driver repository | Device commands, transport, response decoding, and device-level tests          |
| `lab-instruments`            | A capability-oriented bridge, such as the Byonoy plate-reader interface        |
| Reviewed document loader     | Parse and validate a versioned device document into a typed payload            |
| `DocumentExecutor`           | Execute that payload and report progress or failure                            |
| Adapter runtime registration | Associate implementation and format with loaders and simulation/live factories |

The [runtime registration API](https://github.com/lab-lang/lab/blob/master/crates/lab-adapters/src/runtime.rs) is a separate layer above `lab-adapter-api`. A file-only adapter does not need runtime or hardware dependencies.

## Start with an existing executor

Follow [the ODTC registration](https://github.com/lab-lang/lab/blob/master/crates/lab-adapters/src/backend/inheco/odtc/registration.rs) for a thermal document, or the [STAR integration](/docs/instruments/hamilton-star) for reviewed firmware frames.

The current executor interface is:

```rust
pub trait DocumentExecutor {
    fn execute(
        &mut self,
        document: &LoadedReviewedDocument,
        events: &mut dyn EventSink,
    ) -> Result<()>;
}
```

The [source definition](https://github.com/lab-lang/lab/blob/master/crates/lab-runtime/src/execution.rs) uses `anyhow::Result`. `LoadedReviewedDocument` carries a validated typed payload; the executor retrieves the expected payload and executes it. `EventSink` records supported progress events. Returning success reports completion.

Register the loader with `RuntimeDocumentRegistration::new(implementation, format, loader)`, then attach a simulation factory or live executor factory as applicable. Compose that record onto the adapter with `with_runtime_document`. The [native installation instructions](/docs/contributing/procedure-semantics#install-the-native-contribution) apply to both CLI and SDK builds.

## Keep the reviewed boundary intact

Runtime validates the plan and child-document digests before execution. The executor must consume the exact reviewed payload and Asset binding. A retry or resume must not silently substitute a program, profile, or instrument.

Simulation should exercise the same document shape and observable sequencing. Device fakes and recorded responses can establish transport and failure behavior without physical hardware. Live execution is a distinct validation step with its own instrument and configuration evidence.

## Understand the measurement gap

The [Byonoy bridge](https://github.com/lab-lang/lab/blob/master/crates/lab-instruments/src/plate_reader/byonoy.rs) can return typed `PlateData`. The current executor interface returns completion and progress events; it does not expose a general typed result-output API that binds measurements to workflow acceptance.

A complete measurement contribution therefore needs a versioned request contract, reviewed output identities, result persistence and attribution to the run and material, and the downstream acceptance behavior. Those are open implementation work, rather than an existing callback a contributor can fill in. The [Byonoy reference](/docs/instruments/byonoy-absorbance96) lists the present device support.

For a first contribution here, a focused loader, executor failure case, or recorded-response test provides a smaller, independently reviewable result. Changes to the general measurement-output contract should state the intended identities and persistence behavior before expanding into driver-specific code.

## Verify and finish the contribution

The existing EBEF runtime acceptance test exercises explicit reviewed simulation documents, digest-bound resume, and provenance:

```shell
cargo test --locked -p lab-runtime --test ebef_acceptance
```

It uses a test registry and synthetic inventory. It establishes runtime behavior rather than general compiler support for every simulated capability. Use it as a model for a focused fixture covering your loader and executor.

Include the reviewed input, expected events and completion behavior, one failure or resume case, and the observed result. State which evidence comes from a fake device, simulation, or a physical instrument. Update the adapter's service declarations and [status documentation](/docs/status) to match the implemented path.
