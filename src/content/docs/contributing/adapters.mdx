An **adapter** teaches Lab how an instrument can perform shared operations such as liquid transfers, mixing, or thermal cycling. It checks whether the planned work fits the configured instrument and generates its instruction files.

Choose this path when Lab cannot generate files for your instrument, or when its existing adapter lacks a physical feature. For example, you might make the same Python pipetting method produce a protocol for another liquid-handler model. Your adapter handles physical wells, device limits, and the required output format; the scientific recipe stays in the method.

You contribute Rust code for profile validation, feasibility checks, and file generation, with examples showing accepted work, rejected work, and the emitted files. The result gives scientists files they can inspect and use with the intended instrument software or executor.

## Decide whether you need an adapter change

- **Only the values of supported settings differ:** [contribute an instrument profile](/docs/contributing/instrument-profiles).
- **A new model, geometry, physical feature, or output format is needed:** implement or extend an adapter here.
- **The files already exist and need to be sent to hardware by Lab:** [add execution support](/docs/contributing/execution-support).

An adapter can be valuable without a live executor in Lab. The Opentrons integrations, for example, generate files for vendor tooling. If you want Lab to operate the device directly, add that separately once the instruction format is established.

## Start with the preview adapter

The [complete preview adapter](https://github.com/lab-lang/lab/blob/master/examples/contributing/preview-adapter/src/lib.rs) has one direct Lab dependency, `lab-adapter-api`. It accepts canonical pipetting programs and writes inspection files. Its format has no hardware executor, so you can study the entire integration without device setup.

For your own implementation, use the scaffold:

```shell
lab new adapter acme-handler --driver acme.handler
cd acme-handler
cargo test
```

The generated conformance test exercises registration. Its feasibility and lowering placeholders reject work until implemented; successful scaffold tests do not establish device support.

## Implement four responsibilities

| Code                 | What you supply                                                                       |
| -------------------- | ------------------------------------------------------------------------------------- |
| Descriptor           | Supported procedure contracts, features, capability kinds, formats, and service flags |
| Profile validator    | Typed configuration, semantic checks, and canonical profile serialization             |
| Feasibility callback | Whether this exact program can be realized under the profile                          |
| Lowering callback    | Device files and reviewed-document records for the assigned tasks                     |

The current registered lowerer has this signature, shown from the preview adapter:

```rust
fn lower(
    _: &ValidatedAdapterProfile,
    plan: &AdapterInvocationPlan,
    invocation: &AdapterInvocation,
    _: &ProcedureContractRegistry,
) -> Result<AdapterInvocationLowering, AdapterLoweringError>
```

`lab-adapter-api` exports the Lab types in these callbacks. The plan contains allocated tasks; your lowerer selects those assigned to `invocation`. Each emitted document must retain exact task and requirement attribution. The preview implementation shows the traversal and returned records in working code.

The compiler has already selected the method, material sources, offerings, assets, and implementation. Preserve those decisions. A method's biological operation name is retained for attribution; support is determined by the canonical procedure contract and features you can implement.

## Reuse the existing procedure contracts

A pipetting implementation consumes `PipettingProgramV1`; a thermal implementation consumes `ThermalProgramV1`. Rust validates those programs and derives their capabilities. The adapter still owns the physical details: well assignment, geometry, liquid classes, device limits, and vendor output.

Reject a feature or configuration you cannot preserve. For example, accepting tracked liquid-surface aspiration requires a compatible physical realization, not merely emitting an ordinary aspirate command. If the physical operation itself cannot be expressed by an existing contract, follow [Extend procedure semantics](/docs/contributing/procedure-semantics).

## Install and check the adapter

The [native composition instructions](/docs/contributing/procedure-semantics#install-the-native-contribution) connect your crate to the development CLI and SDK. Registration makes the implementation available; a project's manifest must still bind it to an exact Asset, and planning must find compatible offerings and materials.

Run the existing example conformance test:

```shell
cargo test --locked -p lab-project --test contributing
```

It supplies complete allocated programs to the preview adapter and checks emitted programs and material bindings. For your adapter, add focused examples that exercise physical feasibility, unsupported features, and emitted artifact contents. The preview test establishes the registration and allocation boundary, not the semantics of your device.

## Finish the contribution

Include the adapter crate or focused changes, a complete profile, one supported canonical program, a rejected case, and inspectable output. Keep advertised features and service flags aligned with those examples. Declare simulation or runtime support only when their separate implementations are present.

When file generation works, [Run instruments from Lab](/docs/contributing/execution-support) explains reviewed-document loaders and executors. Instrument command encoding and transport usually belong in the corresponding driver repository, with the Lab adapter consuming that library.
