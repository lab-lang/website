Start with the [contribution chooser](/docs/contributing), then install the tools your path uses. These guides describe a checkout of the [Lab repository](https://github.com/lab-lang/lab). Tagged distributions are listed on [GitHub Releases](https://github.com/lab-lang/lab/releases); development APIs may be newer than an installed release or the browser playground.

## Choose your development setup

| Contribution                            | Tools you will use                                                                      |
| --------------------------------------- | --------------------------------------------------------------------------------------- |
| Scientific package or pipetting Method  | Python SDK, an editor, and the package checker                                          |
| Instrument profile or liquid-class data | CLI validator and a consuming example                                                   |
| Builder, contract, adapter, or executor | Rust workspace and focused crate tests; rebuild the SDK when testing Python integration |

Python and configuration authors do not need to read or change Rust. Building the development SDK from source still requires a Rust toolchain and `uv`; use the requirements recorded in the checkout's `Cargo.toml` and `crates/lab-python/pyproject.toml`.

## Python SDK

From the Lab repository root:

```shell
cd crates/lab-python
uv sync --locked --all-groups
```

Return to the repository root after installation. The examples name `crates/lab-python/.venv/bin/python` explicitly so they use this SDK. Changing a Python Method or its Lab declarations needs no native rebuild; regenerate its Method JSON or bindings as directed by that path.

Continue to [Add scientific vocabulary](/docs/contributing/scientific-vocabulary) or [Write a pipetting method](/docs/contributing/pipetting-methods).

## Native CLI and compiler tools

From the repository root, build the workspace:

```shell
cargo build --locked --workspace
```

`cargo build` produces two binaries you'll use directly: `lab`, the
package-aware CLI, and `labc`, the single-file developer compiler used
throughout this documentation for `--emit` inspection. A third, `lab-opt`,
operates on textual LAIR rather than source and is covered in
[CLI reference](/docs/compiler/cli). They land in
`target/debug/`, so put that on your `PATH` to run them by name below.

For a package check without changing `PATH`, use `cargo run --locked -p lab-cli -- check <package>`. [Instrument profiles](/docs/contributing/instrument-profiles) use the resulting CLI. Native contributors should follow the focused test and [registration instructions](/docs/contributing/procedure-semantics#install-the-native-contribution) for their extension.

## Scaffold a project

```shell
lab new project my-plasmid
```

`lab new` writes a minimal package:

```text
my-plasmid/
  lab.toml
  .gitignore
  src/
    programs/
      main.lab
```

`lab.toml` declares the package name, version, edition, and build entry
point. Source lives under `src/`, conventionally split into `designs/`,
`workflows/`, and `programs/`. A facility-aware package adds an SBOLInventory
document under `inventory/` and checked implementation profiles under
`adapters/`. `lab new` only scaffolds `src/programs/main.lab` to start.
[Modules and packages](/docs/language/modules-and-packages) covers the full
manifest shape and module naming convention.

## Check, build, and inspect

```shell
lab check my-plasmid
lab build my-plasmid
lab metadata my-plasmid
```

`lab check` resolves imports, type-checks, and verifies material flow for a
single `.lab` file or a whole project. `lab build` does the same and then
writes one `*.module.json` artifact per module plus a package index and a
`lab.lock` file under `.lab/build/`. When the package declares an inventory,
the same command allocates reachable requirements across its selected Facility
and emits reviewed asset bundles. A package without an inventory stops at
portable compiler artifacts. `lab metadata`
prints the resolved manifest and module list without compiling anything,
useful for confirming `lab.toml` resolved the way you expect before a build.

Every `lab` subcommand accepts a global `--json` flag for machine-readable
output, which is what the language server and other tooling consume instead
of parsing human-readable text.

## Inspecting a single file

For working on the language itself, or on a single design outside a package,
`labc` is faster to iterate with: it takes one `.lab` file and an `--emit`
target directly, without a `lab.toml`.

```shell
labc reporter.lab --emit module-ir
```

See [CLI reference](/docs/compiler/cli) for the full table of `--emit` representations. `labc` inspects portable compiler artifacts; use `lab build` with a facility configuration to generate device bundles.
