Lab is an experimental compiler with a working end-to-end facility vertical slice. Parsing a model, planning against it, simulating it, and controlling physical hardware are different support claims; this page keeps those claims separate.

## Implemented today

| Area               | Current support                                                                                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frontends          | Lab and Python both produce the same checked portable module representation.                                                                                                      |
| Language           | Packages, modules, typed declarations, roles, quantities, workflows, action contracts, acceptance claims, and affine material ownership.                                          |
| LAIR               | Design, Workflow, and Protocol dialects; one plasmid-build conversion; textual IR; whole-module material-linearity analysis; one registered pass.                                 |
| Facility ingestion | Turtle, RDF/XML, JSON-LD, and N-Triples through SBOLInventory Profile 0.2 validation; optional exact Facility selector with single-Facility inference.                            |
| Materials          | Exact design Component IRI to active MaterialLot `sbol:built` matching; no display-name matching; ambiguity fails closed.                                                         |
| Requirements       | Typed reachable capability requirements with qualification, control mode, parameter, source, and call-site identity.                                                              |
| Allocation         | Exact `Requirement -> CapabilityOffering -> Asset` bindings over one immutable inventory snapshot, with rejection explanations and adapter eligibility.                           |
| Adapters           | Descriptor catalog, semantic capabilities separated from features, explicit Asset bindings, checked canonical profiles, and frozen profile hashes.                                |
| Reviewed plans     | `lab.execution-plan.v0` with inventory, facility, lot, offering, Asset, adapter, DAG, movement, child-document, and digest bindings.                                              |
| Runtime            | Whole-plan preflight, dry-run narration, simulation path, exact executor registry, confirmation gates, durable ledger, digest-bound resume, and supported STAR/ODTC live paths.   |
| Provenance         | A new conformant inventory result document with Activities, Usages, output MaterialLots, lineage, ExperimentalData, and evidence Attachments; source inventory remains unchanged. |

## Device implementation matrix

An adapter is an implementation bound to one exact Asset; it is not the Asset or the facility model. Service flags are intentionally independent.

| Adapter               | Semantic capabilities                               | Planning | Program lowering                                                        | Simulation          | Runtime     |
| --------------------- | --------------------------------------------------- | -------- | ----------------------------------------------------------------------- | ------------------- | ----------- |
| `opentrons.ot2`       | Liquid handling, thermal cycling                    | Yes      | Python protocol bundles                                                 | No built-in runtime | No          |
| `opentrons.flex`      | Liquid handling, thermal cycling                    | Yes      | Protocol Designer JSON                                                  | No built-in runtime | No          |
| `hamilton.star`       | Liquid handling                                     | Yes      | `lab.star-run.v0`                                                       | Yes                 | Yes         |
| `inheco.odtc`         | Thermal cycling                                     | Yes      | Consumes device-neutral thermocycle documents; no whole-program lowerer | Yes                 | Yes         |
| `byonoy.absorbance96` | Absorbance measurement                              | No       | No                                                                      | No                  | No          |
| `lab.simulator`       | Liquid handling, incubation, absorbance measurement | Yes      | Consumes semantic simulation documents                                  | Yes                 | No hardware |

The Byonoy driver and capability trait exist, but no compiler path currently allocates and lowers a plate-read invocation to it. Opentrons outputs are generated and can be checked with vendor tooling, but Lab does not directly execute those protocols. Physical hardware operation always requires facility-specific review and qualification beyond what the repository can claim.

## Transitional architecture

The current plasmid-build path selects Golden Gate during Workflow-to-Protocol conversion and derives facility requirements through a separate checked-module projection. This works for the vertical slice but is not the accepted general architecture.

The replacement keeps Lab as a multi-layer IR compiler:

```text
design-intent
    -> refined method alternatives containing Procedure and Capability IR
    -> joint method and facility solving
    -> allocated-procedure
    -> immutable adapter invocations
```

The required implementation work includes an RDF-free `lab-capability` semantic crate, first-class Method/Procedure/Capability LAIR, declarative method packages for Rust and Python, one authoritative requirement analysis over LAIR, a global constraint model, allocation applied back to exact IR identities, and adapter invocation schemas that do not expose Pliron.

## Important current limits

- The standard library declares more actions than the current LAIR lowering implements.
- Method alternatives and joint method/facility selection are not yet represented; the initial plasmid build has one compiler-selected route.
- Allocation has no general reservation service, calendar, queue, consumable depletion, or dynamic rescheduling.
- Inventory is a checked snapshot, not a live LIMS or booking system.
- Most EBEF capability kinds have semantic catalog coverage but no Lab method library, procedure lowering, adapter, simulator model, or evidence schema yet.
- Package dependencies are local paths only; registry requirements are rejected rather than partially resolved.
- Generated procedures are not automatically qualified laboratory protocols.

## Why the EBEF example matters

Caltech's Ecology and Biosphere Engineering Facility demonstrates the intended scale: nested laboratory and controlled-environment Zones, dozens of Assets, and offerings spanning liquid handling, incubation, microscopy, electrochemistry, plant growth, sterilization, storage, and measurement. Its public catalog validates as a descriptive SBOLInventory graph, while a separate synthetic extension exercises a three-capability simulated workflow.

The example deliberately does not infer adapters, control paths, or executable qualification from a public equipment page. Moving an EBEF Asset from `Described` to `Plannable`, `Simulatable`, `Executable`, or `Qualified` requires progressively stronger operational facts and evidence.
