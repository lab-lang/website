Lab is an experimental compiler for checking protocols, producing typeset documents, and helping automate suitable laboratory work. This page records current support for each use, from source checking and document generation through facility planning and device execution.

## Implemented today

| Area               | Current support                                                                                                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Frontends          | Lab and Python produce the same checked portable module representation.                                                                                                                                                  |
| Language           | Packages, modules, typed declarations, roles, quantities, workflows, action contracts, acceptance claims, and affine material ownership.                                                                                 |
| Protocol documents | Facility builds produce operator documents and manual run sheets as editable Typst sources, with PDF rendering in the CLI. Content and typography have separate implementations.                                         |
| LAIR               | Design, Workflow, Method, Procedure, Capability, Allocation, and Meta dialects; verifier-valid `design-intent`, `refined-alternatives`, and `allocated-procedure`; textual IR; whole-module material-linearity analysis. |
| Methods            | RDF-free `lab.method-catalog.v2`, standard and package-contributed registries, real alternatives, typed Procedure values and materials, and Python authoring and persistence through the same Rust validator.            |
| Python Procedures  | `lab.procedures.pipetting` provides typed templates, logical vessel handles, exact volumes, task-parameter references, fluid paths, and portable techniques in the development SDK.                                      |
| Facility ingestion | Turtle, RDF/XML, JSON-LD, and N-Triples through SBOLInventory Profile 0.2 validation; optional exact Facility selector with single-Facility inference.                                                                   |
| Materials          | Exact design Component IRI to active MaterialLot `sbol:built` matching; no display-name matching; exact selected lot identities are frozen into allocation.                                                              |
| Requirements       | First-class requirements produced by Method refinement with exact Capability and property IRIs, qualification, control mode, typed constraints, Procedure ownership, and ancestry.                                       |
| Allocation         | `lab.planning-problem.v2`, joint Method and facility solving, `lab.facility-planning-solution.v3`, solution application to Allocated Procedure LAIR, and explained rejection or ambiguity.                               |
| Adapters           | `lab.adapter-catalog.v4`, semantic capabilities separated from features, explicit Asset bindings, checked canonical profiles, frozen hashes, and `lab.adapter-invocations.v3`.                                           |
| Device lowering    | OT-2, Flex, STAR, and ODTC lower supported exact allocated Procedure tasks and emit one Requirement-attributed reviewed child document per supported task.                                                               |
| Reviewed plans     | `lab.execution-plan.v4` with compiler-evidence, inventory, Method, task, lot, offering, Asset, adapter, DAG, movement, child-document, and digest bindings.                                                              |
| Runtime            | Whole-plan preflight, dry-run narration, simulation, exact executor registry, confirmation gates, durable ledger, digest-bound resume, and selected STAR/ODTC live paths.                                                |
| Provenance         | A new conformant inventory result document with Activities, Usages, output MaterialLots, lineage, ExperimentalData, and evidence Attachments; source inventory remains unchanged.                                        |

## Device implementation matrix

An adapter is an implementation bound to one exact Asset; it is not the Asset or facility model. Service flags are intentionally independent.

| Adapter               | Semantic capabilities                    | Planning | Exact-task lowering                                 | Simulation          | Runtime     |
| --------------------- | ---------------------------------------- | -------- | --------------------------------------------------- | ------------------- | ----------- |
| `opentrons.ot2`       | Liquid handling, thermal cycling         | Yes      | Python protocol per supported task                  | No built-in runtime | No          |
| `opentrons.flex`      | Liquid handling, thermal cycling         | Yes      | Protocol Designer JSON per supported task           | No built-in runtime | No          |
| `hamilton.star`       | Liquid handling                          | Yes      | `lab.star-run.v0` per supported task                | Yes                 | Yes         |
| `inheco.odtc`         | Thermal cycling                          | Yes      | `lab.thermocycle-run.v1` per supported thermal task | Yes                 | Yes         |
| `byonoy.absorbance96` | Absorbance measurement                   | No       | No                                                  | No                  | No          |
| `lab.simulator`       | Canonical pipetting and thermal programs | Yes      | Semantic simulation documents                       | Yes                 | No hardware |

The Byonoy driver and capability trait exist, but no compiler path currently allocates and lowers a plate-read invocation to it. Opentrons outputs are generated and can be checked with vendor tooling, but Lab does not directly execute them. ODTC lowering exists; its registration still advertises `Sila2` while its driver implements SiLA 1.x, an unresolved control-mode mismatch. Physical hardware operation requires facility-specific review and qualification.

## Canonical compiler architecture

The production package and Python planning path is now:

```text
design-intent
    -> refined Method alternatives containing Procedure and Capability IR
    -> joint Method and facility solving
    -> allocated-procedure
    -> immutable exact-task adapter invocations
```

The fixed Protocol dialect, pre-facility Golden Gate conversion, separate checked-module requirement projection, and whole-program automation backend path have been removed. `lab build`, `lab plan`, and Python planning use the same `lab-project` service.

This architecture matters because it eliminates false breadth. A recognized Capability IRI, an installed device driver, an adapter descriptor, a validated profile, a generated document, a simulator, a live executor, and a qualified physical procedure are distinct milestones. The catalog and reviewed plan retain those distinctions rather than promoting one into another.

## Important current limits

- Document generation currently consumes facility build artifacts. A direct document path from a checked protocol, including its branches and scientific context, is planned in the [compiler architecture](/docs/compiler/pipeline#protocol-documents).
- The built-in Method registry covers the current Golden Gate Intent slice. Packages can add portable Methods without changing compiler Rust, but the repository does not yet provide a broad community catalog for general laboratory work.
- Generic action lowering preserves exact checked declaration identities; refinement requires a compatible Method for each reachable action. The bundled Method library covers a smaller vocabulary than the standard library declares.
- Runnable lowering rejects workflow state, conditionals, matches, loops, triggers, and event emission. Those constructs can be checked in portable modules, but are not flattened into linear runnable programs.
- OT-2, Flex, STAR, and ODTC consume supported versioned Procedure contracts and features. New scientific Methods can reuse those contracts; new physical semantics require corresponding contract and adapter work.
- Independently emitted task documents require staging. Logical material lineage does not automatically propagate physical well locations or liquid-class assignments across device files.
- General instrument measurement outputs are not yet connected to workflow acceptance decisions.
- Allocation has no general reservation service, calendar, queue, consumable depletion, dynamic rescheduling, or complete facility movement optimizer.
- Inventory is a checked snapshot, not a live LIMS or booking system.
- Most EBEF Capability kinds still have no Lab Method definition, Procedure lowering, adapter, simulator model, or evidence schema.
- Package dependencies are local paths only; registry requirements are rejected rather than partially resolved.
- Generated procedures are not automatically qualified laboratory protocols.

## Why the EBEF example matters

Caltech's Ecology and Biosphere Engineering Facility demonstrates the intended scale: nested laboratory and controlled-environment Zones, dozens of Assets, and offerings spanning liquid handling, incubation, microscopy, electrochemistry, plant growth, sterilization, storage, and measurement. Its public catalog validates as a descriptive SBOLInventory graph, while a separate synthetic extension exercises a three-capability simulated workflow.

The example deliberately does not infer adapters, control paths, or executable qualification from a public equipment page. Moving an EBEF Asset from `Described` to `Plannable`, `Simulatable`, `Executable`, or `Qualified` requires progressively stronger operational facts and evidence.
