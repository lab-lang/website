Support varies by feature, and by compiler phase within a feature: parsing
something is not the same as executing it. This page tracks the gaps
concretely enough to act on; when a design document describes more than the
implementation covers, the implementation is what's true today.

## Standard library

Five of the eight bundled `std` modules are written in Lab rather than in
Rust: `std.bio.designs`, `std.bio.golden_gate`, `std.bio.parts`,
`std.bio.backbones`, and `std.bio.reporters`. Nothing in the checker
distinguishes them from a package, and their own documentation comments are
their reference entries. A module needing pure functions or durable action
contracts stays in Rust, because neither has a source declaration form yet.

Twelve of the seventeen `std.lab.plasmid` contracts type-check but have no
LAIR lowering yet: `capture`, `synthesize`, `assemble`, `pick`, `screen`,
`grow`, `purify`, `split`, `sequence`, `quantify`, `store`, and `dispose`.
Only `provision`, `transform`, `recover`, `dilute`, and `plate` reach LAIR
directly, plus the separate `realize` effect from `std.bio.build`, which the
Protocol dialect conversion expands into synthesize and assemble operations
internally. `realize` produces a plasmid and `transform` produces a strain,
so a build graph spans both artifact kinds. See
[Action contracts](/docs/guide/action-contracts) for the full table and
[LAIR dialects](/docs/compiler/lair-dialects) for how that expansion works.

## Backends

A target profile's `[target] backend` key selects both the profile schema and
the backend that compiles the build, so `lab build --target <name>` compiles
for whichever machine the named profile declares. An absent key means
`opentrons.ot2`, so every project written before there was a choice builds
unchanged, and an unknown backend is an error naming the ones this toolchain
provides. Two profiles over the same program yield two packages with the same
wave structure, manifest schema, and manual-protocol shape.

| Backend        | Profile key      | Emits                    | Checked against                  |
| -------------- | ---------------- | ------------------------ | -------------------------------- |
| Opentrons OT-2 | `opentrons.ot2`  | Python, API level 2.21   | The official Opentrons simulator |
| Opentrons Flex | `opentrons.flex` | JSON protocols, schema 8 | `opentrons analyze`              |

Both are experimental. Deck layout, labware, instruments, and capacity come
from a target profile rather than from constants, and allocation spills
across every plate a profile declares. Each validates a design's reaction
balance against its own stated volume, replicate and dilution bounds, plate
capacity, source-rack capacity, and tip capacity. Each keeps its own spelling
of every profile field it interprets, so a Flex profile naming an OT-2
pipette fails validation with a sentence rather than a robot-side rejection.

Neither yet queries a live inventory service, resolves inventory lots, ingests
SBOL, designs compatible overhangs, normalizes source concentrations, prepares
DNA between dependent waves, or attaches runtime evidence to acceptance
decisions. See [Opentrons OT-2](/docs/backends/opentrons-ot2) and
[Opentrons Flex](/docs/backends/opentrons-flex).

### Backend roadmap

**Hamilton STAR** is next: a typed firmware protocol and USB transport for the
STAR and STARlet, which takes Lab off the Opentrons family and onto a bench
that is driven by firmware commands rather than by an uploaded protocol
document. Dispatch is a closed match over the concrete profile and backend
pairs today rather than a registry, which is the shape that holds until a
backend arrives that cannot be listed at compile time.

## Editor tooling

LSP over stdio, plus a WebAssembly API and a VS Code extension. Completion
and hover carry the documentation each declaration was written with, and a
`use` path hovers the module it imports. Definition, references, and rename
only see open documents: there's no persistent, project-wide symbol index
yet. Formatting is whitespace-only. Parse recovery surfaces a single
diagnostic at a time rather than recovering past the first syntax error. See
[Editor support](/docs/tooling/editor-support).
