The Hamilton STAR/STARlet integration is the most complete live adapter in Lab. An exact SBOLInventory Asset is bound to `hamilton.star`; global allocation assigns exact liquid-handling Procedure tasks to one qualified offering on that Asset; the adapter plans against a checked carrier-and-rail profile and emits `lab.star-run.v0` documents. Runtime replays the reviewed frames verbatim, adding only protocol command IDs.

To contribute configuration or liquid-handling knowledge, start with [Configure a supported instrument](/docs/contributing/instrument-profiles). For device features or file generation, follow [Generate instrument files](/docs/contributing/adapters).

## Bind the Asset

```toml
[[execution.adapters]]
asset = "https://example.org/my-lab/hamilton_star"
driver = "hamilton.star"
profile = "adapters/hamilton-star.toml"
```

The adapter supports liquid handling under `ReviewedFile` or `Api` control and declares planning, lowering, simulation, and runtime services. That descriptor is an implementation claim, not a facility claim: the inventory offering still determines activity, qualification, and control mode.

## Carrier and rail planning

STAR profiles place catalog carriers on one-based rails and address labware as `<carrier>/<site>`. The checked catalog carries carrier geometry, labware capacity, and volume-to-height models.

```toml
[machine]
variant = "starlet"
channels = 8

[deck.carriers.tips]
catalog = "tip_carrier_480"
rail = 1

[deck.carriers.plates]
catalog = "plate_carrier_l5"
rail = 9

[deck.reaction_plate]
site = "plates/1"
labware = "pcr_plate_96"
capacity = 96
```

Validation rejects a carrier outside the machine's rail span, overlaps, nonexistent sites, two resources on one site, labware/category mistakes, capacity contradictions, and unknown fields. The planner tracks well volume, computes liquid heights with explicit safety margins, and choreographs transfers for the supported eight-channel arm.

## Reviewed frames are the execution boundary

The adapter selects its assigned tasks from `lab.adapter-invocations.v3` and lowers supported `PipettingProgramV1` programs. Rust validates canonical liquid operations, units, material interfaces, and capability ownership; STAR code applies geometry, liquid classes, and physical constraints, then emits one typed `lab.star-run.v0` document per supported task. A [Python pipetting Method](/docs/contributing/pipetting-methods) reaches this same contract without adding a biological action name to the adapter. Each document contains machine identity, channel count, ordered firmware frames, operator-facing descriptions, and manual steps. The facility execution plan freezes its digest and exact Method, task, requirement, offering, Asset, adapter, and profile bindings.

```shell
lab run .lab/plan --dry-run
lab run .lab/plan --simulate
lab run .lab/plan --asset-endpoint https://example.org/my-lab/hamilton_star=usb://star
```

Preflight parses every child document and verifies the complete reviewed closure before opening any executor. Live execution sends only the frozen frames, performs the defined Z-safety response on firmware failure, records a durable ledger keyed to the plan digest, and refuses resume if any reviewed input changed.

## Multi-Asset procedures

A STAR does not become a workcell when a thermocycler or reader is nearby. Those instruments are separate Assets with their own capability offerings and adapters. The facility-wide Procedure graph contains explicit material movement and dependencies between allocated tasks. This is what lets the same architecture compose a STAR, an [Inheco ODTC](/docs/instruments/inheco-odtc), a reader, and manual work without inventing one closed machine category.

## Current boundary

The adapter is experimental. Its catalog and planner cover a bounded set of carriers, labware, the eight-channel arm, and declared pipetting features. Each task is independently staged; upstream logical material references do not automatically propagate physical locations or liquid-class assignments between documents. Live execution needs facility-specific endpoints and qualification. Extending a supported Method can reuse the pipetting contract; adding a physical feature requires corresponding shared semantics and a checked STAR implementation.
