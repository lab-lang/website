The OT-2 integration is a Lab adapter, not a compiler target. An SBOLInventory graph describes the physical OT-2 Asset and its qualified capability offerings. `lab.toml` explicitly binds that exact Asset IRI to the `opentrons.ot2` implementation. Global facility planning selects Methods and exact resources; only then may the adapter lower the tasks assigned to its invocation.

To contribute configuration or liquid-handling knowledge, start with [Configure a supported instrument](/docs/contributing/instrument-profiles). For device features or file generation, follow [Generate instrument files](/docs/contributing/adapters).

## Bind an installed Asset

```toml
[inventory]
document = "inventory/facility.ttl"

[[execution.adapters]]
asset = "https://example.org/my-lab/opentrons_ot2"
driver = "opentrons.ot2"
profile = "adapters/opentrons-ot2.toml"
```

The adapter declares exact support for SBOLInventory `LiquidHandling` and `ThermalCycling` under `ReviewedFile` control. It provides planning compatibility and exact-task lowering and emits standalone Opentrons Python protocols. It does not claim a Lab-managed live runtime or built-in simulation service.

The binding does not make the Asset executable by itself. Each selected offering must independently carry sufficient qualification and a compatible control mode in the inventory graph. Conversely, product metadata in RDF never causes Lab to select this driver.

## Checked implementation profile

The adapter profile describes residual machine configuration: Protocol API level, pipette models and mounts, modules, deck positions, labware, and task capacity. It cannot name an Asset or another driver. Unknown fields, invalid slots, module collisions, incompatible pipettes, and capacity contradictions fail during validation.

```toml
[protocol]
api_level = "2.21"

[instruments.small]
model = "p20_single_gen2"
mount = "left"

[instruments.large]
model = "p300_single_gen2"
mount = "right"

[deck.thermocycler]
model = "thermocycler module gen2"
labware = "nest_96_wellplate_100ul_pcr_full_skirt"
capacity = 96
```

`lab adapters validate opentrons.ot2 adapters/opentrons-ot2.toml` validates the profile directly. During planning, Lab stages its canonical form and freezes the SHA-256 in the adapter binding, invocation, and reviewed plan.

## Exact Procedure lowering

The OT-2 lowerer selects its assigned tasks from `lab.adapter-invocations.v3`. Those tasks carry canonical `PipettingProgramV1` or `ThermalProgramV1` programs with validated parameters, units, material interfaces, and capability requirements. Golden Gate setup and cycling, transformation, and dilution are examples of Methods producing these contracts.

The adapter checks contract features and physical feasibility, assigns wells, validates deck and tip capacity, and renders the supported program. A new [Python pipetting Method](/docs/contributing/pipetting-methods) can use this boundary without adding its biological action name to the adapter. It must still fit the adapter's supported features and the selected profile.

## Output

For an allocated Asset whose readable identity is `opentrons_ot2`, each supported task gets its own review directory:

```text
.lab/build/assets/opentrons_ot2/
└── tasks/
    ├── 001-setup-golden-gate-reaction/
    │   ├── automation_protocol.py
    │   ├── invocation_manifest.json
    │   └── manual_protocol.pdf
    ├── 002-thermal-cycle-golden-gate-reaction/
    │   ├── automation_protocol.py
    │   ├── invocation_manifest.json
    │   └── manual_protocol.pdf
    └── 005-serial-dilution/
        ├── automation_protocol.py
        ├── invocation_manifest.json
        └── manual_protocol.pdf
```

The embedded `lab.opentrons-ot2-task.v1` plan freezes the Facility, Asset, adapter profile, exact Requirement and offering, observed qualification and control mode, Procedure operation, typed ports and parameters, material sources, deck, and resource allocation. `plan.execution.json` references each independently executable Python protocol by Requirement and digest.

## Current boundary

The adapter is experimental. Its declared contract features and physical profile bound the programs it can lower. Each emitted Procedure is independently staged: a logical dependency on an upstream material does not automatically carry physical well locations across protocol files. Lab emits reviewed Python files but does not upload or execute them on an OT-2. Vendor-tool validation and facility-specific qualification remain necessary for physical use.
