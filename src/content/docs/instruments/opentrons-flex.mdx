The Flex integration demonstrates that semantic requirements and device implementation are separate. A Flex Asset can expose the same liquid-handling and thermal-cycling capability kinds as an [OT-2](/docs/instruments/opentrons-ot2), while its deck, pipettes, modules, profile schema, and emitted protocol format remain Flex-specific.

To contribute configuration or liquid-handling knowledge, start with [Configure a supported instrument](/docs/contributing/instrument-profiles). For device features or file generation, follow [Generate instrument files](/docs/contributing/adapters).

## Bind a Flex Asset

```toml
[[execution.adapters]]
asset = "https://example.org/my-lab/opentrons_flex"
driver = "opentrons.flex"
profile = "adapters/opentrons-flex.toml"
```

The `opentrons.flex` descriptor supports `LiquidHandling` and `ThermalCycling` under `ReviewedFile` control. It provides planning compatibility and exact-task lowering and emits Opentrons Protocol Designer JSON. It does not provide a Lab-managed simulation or live-runtime service.

Global allocation selects an exact Method, CapabilityOffering, Asset, material source, and adapter before this code runs. Neither manufacturer/model inference nor a CLI target flag participates.

## The profile is device-specific on purpose

A shared facility vocabulary should not flatten real implementation differences. Flex slots are `A1` through `D3`, Flex pipettes have their own model identifiers, modules have Flex-specific constraints, and trash is a movable addressable area:

```toml
[instruments.small]
model = "p50_single_flex"
mount = "left"

[instruments.large]
model = "p1000_single_flex"
mount = "right"

[deck.trash]
area = "movableTrashA3"
```

The explicit driver chooses this schema before the profile is parsed. A profile that names an OT-2 pipette, places labware beneath a thermocycler, uses a staging slot, or contains an unknown key fails before planning.

## Exact Procedure and typed JSON lowering

Flex consumes allocated `PipettingProgramV1` and `ThermalProgramV1` tasks, using the same canonical contracts as the OT-2 implementation. Rust validates parameters, units, material interfaces, and capability requirements; the Flex adapter checks supported features and physical feasibility before deck planning. A [Python pipetting Method](/docs/contributing/pipetting-methods) uses this contract without a new biological-operation branch in the adapter.

The emitter builds Protocol Designer schema 8 documents through a typed Rust authoring layer. Loaded labware, modules, and pipettes become typed handles; commands accept only compatible handles; embedded standard labware definitions validate well names and volumes. Flex-specific resource allocation and JSON construction remain inside this adapter.

Each supported task produces a `lab.opentrons-flex-task.v1` invocation manifest, one independently reviewed `automation_protocol.json`, and an operator PDF under `assets/<asset>/tasks/<task>/`. The facility-wide execution plan ties the child document to its exact Requirement, offering, Asset, profile, and digest.

## Current boundary

The adapter is experimental and provides planning compatibility and lowering. Its descriptor and profile bound supported Procedure features and physical layouts. Each emitted task is independently staged; material dependencies do not automatically propagate physical locations across files. Generated Protocol Designer documents require vendor-tool validation, review, and facility-specific qualification. Lab provides no built-in Flex simulation or live executor.
