Structured data has one declaration form, `record`. What a record is _for_ is
a **role** it plays, declared with `is`. Set against every kind of immutable
information stands `material`, which has physical identity and cannot be
copied. That split is the foundation the rest of the language's checking
builds on.

| Value             | Carries                                               | Copyable   |
| ----------------- | ----------------------------------------------------- | ---------- |
| `record`          | Immutable structured information                      | Yes        |
| An artifact       | Immutable biological intent, such as a plasmid design | Yes        |
| `Material<T>`     | Physical identity: a real sample, culture, or plate   | No, affine |
| `is Evidential`   | A record that may be offered in support of a claim    | Yes        |
| `is Event`        | A record `emit` and `when` resolve against            | Yes        |
| `record` + `case` | A tagged result a workflow settles into               | Yes        |

A word is meaningful only where the compiler assigns a law to it, so there is
no declaration keyword the compiler reads nothing from. `observation`,
`evidence`, `event`, and `outcome` are not keywords: they are records that
play a role, or records with `case` constructors.

## Roles classify types

A role is a name that types can play. It has no values of its own, which is
why it may bound a type parameter and may never be the type of anything.

```lab
role Inducer

record Arabinose is Inducer
record Tetracycline is Inducer
```

Membership is declared by the type that plays the role rather than listed by
the role, so a package can classify its own types against a role it imported
and a role stays open to types that do not exist yet. That is why a role has
no block listing its members. Writing a role where a type belongs is an error
that names both ways forward: name the parameter (`<T: Signal>`), or name a
type that plays it.

## Why `material` is different

An artifact declaration describes a plasmid; a `Material<Plasmid>` _is_ a
tube of it sitting in a rack. Two workflows can both read the same design
freely, the same way two functions can both read the same constant, since a
design has no physical existence to run out of. A material does. Once a
workflow takes ownership of a culture, no other workflow can also take it:
there is only one tube.

This is why material values are **affine** rather than freely copyable. The
checker tracks every material-typed value through a workflow and rejects
programs that would use one after giving it away, lose it silently on some
path through a branch, or hold inconsistent ownership where two branches of
an `if` disagree about who has it. See
[Material flow and acceptance](/docs/guide/material-flow-and-acceptance) for
exactly which patterns are rejected and why.

## Evidence is not automatically proof

A record that plays `Evidential` is shaped to be offered against an `accept`
predicate. Having evidence of the right shape does not mean a claim passed;
it means there is now something to check the claim against. Whether it
satisfies the predicate is a runtime judgment made once real measurements
exist.

How much evidence a claim needs is written down too. `across 3 biological
replicates` says a claim is believed on three independent transformants
rather than three readings of one culture, and the compiler knows the
difference because it knows where each sample came from.

## Tagged results are workflow endpoints

A record with `case` constructors is what a workflow's branches settle into:
`Ready` and `TimedOut` in a reactive workflow, or `Accepted` and `Rejected`
in a build. Both cases share the fields declared above them, so a plate that
never grew still carries the observations that say so.

```lab
record ColonyGrowth:
  plate: Material<Plate>
  observations: List<PlateObservation>

  case Ready:
    colonies: ColonyMap

  case TimedOut
```

They are matched with `match`/`case`, and are the shape a workflow's declared
result type takes.
