This walks through a real plasmid from an empty directory to generated
protocols. Everything here runs against the toolchain as it stands today.

## Install

`lab` is the command line for Lab. It manages projects and packages, and it
is where live laboratory operations will land once there is a runtime to
operate.

```shell
curl -sSf https://www.lab-compiler.org/install.sh | sh
```

That installs `lab`, `labc`, and `lab-opt` into `~/.lab/bin` and wires it into
your shell's `PATH`.

## Create a project

```shell
lab new tet-reporter
cd tet-reporter
```

You get a manifest, one program module, and a `.gitignore` for the generated
`.lab/` directory:

```toml lab.toml
[package]
name = "tet-reporter"
version = "0.1.0"
edition = "2026"

[build]
entry = "src/programs/main.lab"
```

```lab src/programs/main.lab
use std.bio.build
use std.bio.designs

build plasmid starter:
  sequence = dna("ATGCGTACGTTAGCTA")
  require topology == circular
  accept sequence == design.sequence

workflow main() -> Material<Plasmid>:
  product <- realize starter
  return product
```

`plasmid` is not a keyword. `std.bio.designs` declares it with `artifact`,
together with the schema every plasmid is checked against; the compiler knows
only the shape, being a word, a name, and a block of properties, and nothing about
biology. A package of your own can declare words the standard library never
heard of, and a word no imported package declares is an error that lists the
ones in scope.

The plasmid is four lines, and three of them are distinct kinds of claim.
`sequence = …` is a **declarative property**: a deterministic expression
evaluated once and attached to the design, never an effect. `require` is a
constraint checked _before_ anything is built. `accept` is a claim about the
finished material that only runtime evidence can settle.

`main` is separate from all three. Naming a module as the manifest's `entry`
is what makes this package a program rather than a library, and a program
has to state the work it runs, so an entry module must declare
`workflow main`. It is not an ordering directive: build order comes from the
material each call consumes, and `main` is where that dataflow starts.

That distinction is the whole point of the language, so it is worth being
precise about it. The compiler can prove your design is well-typed, and it
can prove a workflow produces the _kinds_ of evidence your `accept` clauses
need. It cannot prove what a future measurement will say. Only the third
judgment — real evidence against the predicate — yields an accepted
material.

Check it:

```shell
lab check
```

```
Checked tet-reporter 0.1.0 (1 modules)
```

## Describe something real

The starter has no components and no way to build it. Replace
`src/programs/main.lab` with a reporter that names the parts it is made of
and says how to realize it.

```lab src/programs/main.lab
use std.bio.build
use std.bio.designs
use std.bio.golden_gate
use std.lab.plasmid

buy:
  part J23101
  part B0034
  part GFP
  part B0015
  backbone pSB1C3
  antibiotic chloramphenicol

  restriction_enzyme BsaI:
    digest_temperature = 37 C

  chassis DH5alpha:
    heat_shock_temperature = 42 C
    recovery_duration = 60 min

/** The GFP reporter under a strong constitutive promoter. */
build plasmid reporter:
  sequence = dna("GCTAGCGGATCCATGACCATGATTACGCCAAGCTTGAATTC")
  backbone = pSB1C3
  components = [J23101, B0034, GFP, B0015]
  restriction_enzyme = BsaI
  assembly_replicates = 1

  require topology == circular

  across 3 biological replicates

  accept sequence == design.sequence
  accept concentration >= 100 ng/uL

/** The reporter carried in a cloning strain. */
build strain reporter_host:
  chassis = DH5alpha
  plasmids = [reporter]
  selection = chloramphenicol
  transformation_replicates = 2
  plating_replicates = 2
  serial_dilutions = 2

workflow assemble_reporter() -> Material<Plasmid>:
  product <- realize reporter
  return product

workflow build_reporter_host(
  reporter: Material<Plasmid>,
) -> (
  strain: Material<Strain>,
  plate: Material<Plate>,
):
  dependencies = [reporter]
  cells <- provision DH5alpha
  strain, culture <- transform reporter_host from dependencies into cells
  culture <- recover culture for 1 h
  culture <- dilute culture
  plate <- plate culture on chloramphenicol
  return strain, plate

workflow main() -> (
  strain: Material<Strain>,
  plate: Material<Plate>,
):
  product <- assemble_reporter
  strain, plate <- build_reporter_host product
  return strain, plate
```

### Where a thing came from is a fact about the thing

`part J23101` under `buy:` declares a value of type `Part` for something a
supplier lists — the block states one origin over everything inside it, and
`buy part J23101` on its own line declares the same thing where there is
only one. Being bought is stated per thing rather than per kind, so `build
plasmid reporter:` and `buy plasmid reference_gfp:` declare the same kind of
thing and differ only in where it came from. `require`, `accept`, and a
place in the build order attach to what is built; an `identity` to order
against attaches to what is bought, and claiming to build something bought
is refused.

An external identity defaults to the declared name, and is written out only
where the two differ:

```lab
buy restriction_enzyme BsaI:
  identity = "NEB-R0535"
```

So the source symbol and the catalog identifier keep separate identities:
renaming `BsaI` in your file and changing which catalog item it points at are
different edits, and only one of them is a rename.

A bought item also carries its own datasheet. The temperature a digest runs
at belongs to the enzyme, so no design has to repeat it, and a design that
departs from the datasheet states its own value and wins.

`components = [J23101, B0034, GFP, B0015]` is a `List<Part>` of checked
symbols. Writing `components = ["J23101"]` is a type error, not a shortcut.

<Callout kind="note">
  A typed identity is not availability. `buy part J23101` says this design
  refers to a catalog item. It says nothing about whether a suitable lot exists,
  how much is left, where it is, or whether you should trust its provenance.
  Those are inventory and runtime questions.
</Callout>

### How much evidence a claim needs

`across 3 biological replicates` says what every claim in the declaration is
believed on. Three colonies picked from a plate are independent
transformants; one culture measured three times is a single organism, so
reporting the second as `n = 3` claims more than the experiment supports. A
single claim may state its own standard instead, which replaces the
declaration's rather than adding to it:

```lab
  accept volume >= 20 uL across 1 biological replicate
```

Which replicates are which is not a property of a sample; it is where the
sample came from. Transformation establishes an organism and picking isolates
independent transformants, while diluting, recovering, plating, and measuring
carry on the lineage that went in.

### The two arrows

The workflow body uses both of Lab's binding forms, and they are not
interchangeable:

- `dependencies = [reporter]` is deterministic evaluation. Replay may run it
  again, because nothing in the world changed.
- `strain, culture <- transform reporter_host from dependencies into cells`
  is a durable effect. It records a command, waits for the completion event,
  and binds the result from that event. **Replay must never repeat it.** You
  cannot un-transform a tube of cells.

Once you have physically consumed something, no runtime can undo it, so Lab
puts that fact in the syntax rather than hiding it behind a function call.

### Materials get used up

`Material<Plasmid>` is affine: it has exactly one owning place. Each action
declares what it does to what you hand it — `copy` for information, `borrow`
to observe without consuming, `take` to consume. `transform` takes both its
dependency material and its cells, so neither name is usable afterward.

Every terminating path must account for everything it owns. Try deleting
`plate` from the return list:

```shell
lab check
```

The checker rejects it: the workflow still owns a plate at a terminating
path, and a plate is not something you can silently drop. Return it, store
it, transfer it, or dispose of it.

## Build

```shell
lab build
```

```
Built tet-reporter 0.1.0 (1 modules)

Build products:
  plasmid tet_reporter

Compiler output: .lab/build
```

Every build writes verified portable module IR under `.lab/build/modules/`, a package index, capability requirement artifacts, and `lab.lock`. For a package with no `[inventory] document`, that is the end of the build: no facility has been selected and no adapter is invoked.

## Describe a facility, then bind its OT-2

A laboratory is an SBOLInventory RDF graph, not a target profile. It contains the Facility, its Zones, installed Assets, exact capability offerings, and MaterialLots. An OT-2 Asset might look like this shortened Turtle:

```turtle inventory/facility.ttl
@prefix cap: <https://sbol.io/ns/capability#> .
@prefix ex: <https://example.org/tet-reporter/> .
@prefix fac: <https://sbol.io/ns/facility#> .
@prefix sbol: <http://sbols.org/v3#> .

ex:facility a sbol:TopLevel, fac:Facility .

ex:opentrons_ot2
    a sbol:TopLevel, fac:Asset ;
    fac:locatedIn ex:automation_zone ;
    fac:capability ex:opentrons_ot2_liquid_handling .

ex:opentrons_ot2_liquid_handling
    a sbol:Identified, fac:CapabilityOffering ;
    fac:capabilityKind cap:LiquidHandling ;
    fac:qualification fac:Executable ;
    fac:controlMode fac:ReviewedFile .
```

The manifest points to that graph and explicitly associates the exact Asset with the installed compiler adapter:

```toml lab.toml
[build]
entry = "src/programs/main.lab"

[inventory]
document = "inventory/facility.ttl"

[[execution.adapters]]
asset = "https://example.org/tet-reporter/opentrons_ot2"
driver = "opentrons.ot2"
profile = "adapters/opentrons-ot2.toml"
```

The adapter profile describes checked deck, pipette, module, and labware configuration. It does not repeat the Asset, capability, qualification, or facility facts, and it cannot select another driver.

```shell
lab build
```

```
Built tet-reporter 0.1.0 (1 modules)

Build products:
  plasmid tet_reporter

Compiler output: .lab/build

Facility outputs:
  Facility: https://example.org/tet-reporter/facility
  Requirements allocated: 5
  Adapter lowerings: 1
  Reviewed plan: .lab/build/plan.execution.json

Asset bundles:
  .lab/build/assets/opentrons_ot2

Automation protocols:
  .lab/build/assets/opentrons_ot2/wave-001/assembly_protocol.py
  .lab/build/assets/opentrons_ot2/wave-002/transformation_protocol.py
  .lab/build/assets/opentrons_ot2/wave-002/plating_protocol.py

Documents:
  .lab/build/assets/opentrons_ot2/dependency_report.pdf
  .lab/build/assets/opentrons_ot2/manual_protocol.pdf
```

The compiler instantiates requirements reachable from `main`, queries the selected Facility, binds each requirement to an exact capability offering and Asset, freezes exact MaterialLot and adapter-profile identities, and invokes only the selected adapter. The output is one asset bundle with one directory per planning wave, all projected from a single reviewed execution plan:

| Path                                            | What it is                                               |
| ----------------------------------------------- | -------------------------------------------------------- |
| `.lab/build/facility_allocation.json`           | Exact requirement, offering, Asset, and lot bindings     |
| `.lab/build/facility_lowering.json`             | Routes from allocations to asset bundles                 |
| `.lab/build/plan.execution.json`                | Reviewed facility-wide dependency DAG and frozen digests |
| `assets/opentrons_ot2/dependency_manifest.json` | The adapter's build graph, waves, and blockers           |
| `assets/opentrons_ot2/dependency_report.pdf`    | A typeset dependency and blocker summary                 |
| `assets/opentrons_ot2/manual_protocol.pdf`      | Typeset instructions with reaction and plate maps        |
| `assets/opentrons_ot2/wave-001/`                | Golden Gate setup and thermocycling                      |
| `assets/opentrons_ot2/wave-002/`                | Transformation, dilution, and selective plating          |

Artifacts in the same wave have no ordering constraint between them, so a
wave is a single robot run over a single deck. Wave 2 cannot start until
wave 1's plasmid physically exists and has been accepted.

Nothing in source names the OT-2, a deck slot, or a pipette. Those facts enter only after the Facility makes an eligible offering available and the manifest binds its exact Asset to the `opentrons.ot2` implementation. Adding a Flex means adding a Flex Asset and offering to the inventory plus an explicit `opentrons.flex` binding; allocation then decides which exact offering can satisfy each requirement. If multiple complete choices remain equally eligible, planning asks for disambiguation rather than silently choosing one.

Use `lab plan` to write just the reviewed facility bundle under `.lab/plan`, and inspect it without hardware:

```shell
lab plan
lab run .lab/plan --dry-run
```

<Callout kind="note">
  **Generated protocols are not qualified protocols.** Before anyone runs this,
  a laboratory must verify source concentrations, overhang compatibility,
  internal restriction sites, labware definitions, deck fit, liquid classes, tip
  policy, transformation conditions, selection media, and organism-specific
  incubation. The compiler validates volumes and capacities. It does not
  validate your biology.
</Callout>
