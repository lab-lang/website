This walks through a real plasmid from an empty directory to generated
protocols. Everything here runs against the toolchain as it stands today.

## Install

`lab` is the command line for Lab. It manages projects and packages, and it
is where live laboratory operations will land once there is a runtime to
operate.

```shell
cargo install --git https://github.com/lab-lang/lab lab-cli --locked
```

That installs `lab` into Cargo's binary directory, normally `~/.cargo/bin`.

## Create a project

```shell
lab new tet-reporter
cd tet-reporter
```

You get a manifest, one program module, and a `.gitignore` for the generated
`.lab/` directory:

```toml lab.toml
[package]
name = "tet-reporter"
version = "0.1.0"
edition = "2026"

[build]
entry = "src/programs/main.lab"
```

```lab src/programs/main.lab
use std.bio.build

plasmid starter:
  sequence: dna("ATGCGTACGTTAGCTA")
  require topology == circular
  accept sequence == design.sequence

workflow main() -> Material<Plasmid>:
  product <- realize starter
  return product
```

The plasmid is four lines, and three of them are distinct kinds of claim.
`sequence:` is a **declarative property**: typed data attached to the
design, not an assignment that runs. `require` is a constraint checked
*before* anything is built. `accept` is a claim about the finished material
that only runtime evidence can settle.

`main` is separate from all three. Naming a module as the manifest's `entry`
is what makes this package a program rather than a library, and a program
has to state the work it runs, so an entry module must declare
`workflow main`. It is not an ordering directive: build order comes from the
material each call consumes, and `main` is where that dataflow starts.

That distinction is the whole point of the language, so it is worth being
precise about it. The compiler can prove your design is well-typed, and it
can prove a workflow produces the *kinds* of evidence your `accept` clauses
need. It cannot prove what a future measurement will say. Only the third
judgment — real evidence against the predicate — yields an accepted
material.

Check it:

```shell
lab check
```

```
Checked tet-reporter 0.1.0 (1 modules)
```

## Describe something real

The starter has no components and no way to build it. Replace
`src/programs/main.lab` with a reporter that names the parts it is made of
and says how to realize it.

```lab src/programs/main.lab
use std.bio.build
use std.bio.inventory
use std.lab.plasmid_actions

J23101 = part("J23101")
B0034 = part("B0034")
GFP = part("GFP")
B0015 = part("B0015")
pSB1C3 = backbone("pSB1C3")
BsaI = restriction_enzyme("BsaI")
DH5alpha = chassis("DH5alpha")
chloramphenicol = antibiotic("chloramphenicol")

plasmid reporter:
  sequence: dna("GCTAGCGGATCCATGACCATGATTACGCCAAGCTTGAATTC")
  backbone: pSB1C3
  components: [J23101, B0034, GFP, B0015]
  restriction_enzyme: BsaI
  assembly_replicates: 1

  require topology == circular
  accept sequence == design.sequence

strain reporter_host:
  chassis: DH5alpha
  plasmids: [reporter]
  selection: chloramphenicol
  transformation_replicates: 2
  plating_replicates: 2
  serial_dilutions: 2

workflow assemble_reporter() -> Material<Plasmid>:
  product <- realize reporter
  return product

workflow build_reporter_host(
  reporter: Material<Plasmid>,
) -> (
  strain: Material<Strain>,
  plate: Material<Plate>,
):
  dependencies = [reporter]
  cells <- provision DH5alpha
  strain, culture <- transform reporter_host from dependencies into cells
  culture <- recover culture for 1 h
  culture <- dilute culture
  plate <- plate culture on chloramphenicol
  return strain, plate

workflow main() -> (
  strain: Material<Strain>,
  plate: Material<Plate>,
):
  product <- assemble_reporter
  strain, plate <- build_reporter_host product
  return strain, plate
```

### Names are typed, not strings

`part("J23101")` is a pure constructor from `std.bio.inventory`. It returns
a value of type `Part` carrying an external inventory identifier. The source
symbol on the left and the string on the right have separate identities:
renaming `J23101` in your file and changing which catalog item it points at
are different edits, and only one of them is a rename.

So `components: [J23101, B0034, GFP, B0015]` is a `List<Part>` of checked
symbols. Writing `components: ["J23101"]` is a type error, not a shortcut.

<Callout kind="note">
  A typed identity is not availability. `part("J23101")` says this design
  refers to a catalog item. It says nothing about whether a suitable lot
  exists, how much is left, where it is, or whether you should trust its
  provenance. Those are inventory and runtime questions.
</Callout>

### The two arrows

The workflow body uses both of Lab's binding forms, and they are not
interchangeable:

- `plasmids = [construct]` is deterministic evaluation. Replay may run it
  again, because nothing in the world changed.
- `strain, culture <- transform reporter_host from plasmids into cells` is a durable effect. It
  records a command, waits for the completion event, and binds the result
  from that event. **Replay must never repeat it.** You cannot un-transform
  a tube of cells.

Once you have physically consumed something, no runtime can undo it, so Lab
puts that fact in the syntax rather than hiding it behind a function call.

### Materials get used up

`Material<Plasmid>` is affine: it has exactly one owning place. Each action
declares what it does to what you hand it — `copy` for information, `borrow`
to observe without consuming, `take` to consume. `transform` takes both its
its plasmids and its cells, so neither name is usable afterward.

Every terminating path must account for everything it owns. Try deleting
`plate` from the return list:

```shell
lab check
```

The checker rejects it: the workflow still owns a plate at a terminating
path, and a plate is not something you can silently drop. Return it, store
it, transfer it, or dispose of it.

## Build

```shell
lab build
```

```
Built tet-reporter 0.1.0 (1 modules)
  Artifacts: .lab/build
```

That writes verified portable module IR under `.lab/build/modules/`, a
package index at `.lab/build/package.json`, and a `lab.lock` next to the
manifest. Portable module IR is the frontend's output boundary: imports
resolved, types checked, action contracts resolved to stable operation
identities, material ownership verified. No laboratory has been chosen yet.

## Lower it to a target

Target specialization is a compiler-development surface today, exposed
through `labc` rather than `lab`. From a checkout of the Lab repository:

```shell
cargo run -p lab-compiler --bin labc -- \
  path/to/tet-reporter/src/programs/main.lab \
  --emit automation-bundle \
  --output-dir /tmp/reporter-build
```

Five files, all projected from a single validated execution plan:

| File | What it is |
| --- | --- |
| `automation_manifest.json` | the construct, well, and handoff plan |
| `manual_protocol.md` | English instructions with reaction and plate maps |
| `assembly_protocol.py` | Golden Gate setup and thermocycling |
| `transformation_protocol.py` | cell transfer, heat shock, recovery |
| `plating_protocol.py` | dilution and selective plating |

Nothing in your source named Golden Gate, heat shock, a deck slot, or a
pipette. The source said `realize`, `transform`, `recover`, `dilute`,
`plate`; the [Opentrons OT-2 backend](/docs/backends/opentrons-ot2) chose
the chemistry and the hardware. A different target may choose differently,
or reject a design it cannot lower.

<Callout kind="note">
  **Generated protocols are not qualified protocols.** Before anyone runs
  this, a laboratory must verify source concentrations, overhang
  compatibility, internal restriction sites, labware definitions, deck fit,
  liquid classes, tip policy, transformation conditions, selection media,
  and organism-specific incubation. The compiler validates volumes and
  capacities. It does not validate your biology.
</Callout>
